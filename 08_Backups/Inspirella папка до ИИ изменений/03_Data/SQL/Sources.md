# Sources

## Зачем нужен этот файл

Этот файл фиксирует source hierarchy Inspirella.

Если `Data Model.md` объясняет, какие сущности существуют, а `Field Dictionary.md` — какие у них поля, то `Sources.md` отвечает на вопрос:

> откуда вообще должны браться данные и почему одним источникам можно доверять больше, чем другим.

Этот файл нужен, чтобы:
- не допустить хаотичного смешивания официальных данных, каталогов и случайных страниц;
- выстроить прозрачную иерархию доверия;
- помочь будущим ИИ-агентам не придумывать данные и не выдавать слабые источники за сильные;
- упростить review, conflict resolution и validation workflows;
- повысить качество базы без избыточной ручной путаницы.

---

## Главная идея source hierarchy

Inspirella строится не просто на большом количестве данных, а на **качественных, проверяемых и осмысленно ранжированных источниках**.

Это особенно важно, потому что проект опирается на три большие опоры:
- персонализацию;
- высокое качество данных;
- низко-хаотичную информационную архитектуру.

Если source layer слабый, то:
- данные начинают противоречить друг другу;
- trust падает;
- персонализация опирается на шум;
- продукт становится менее полезным для реального выбора.

Поэтому в Inspirella действует базовый принцип:

> **не все источники равны, и это должно быть явно зафиксировано.**

---

## Что считается источником

Источник в Inspirella — это любой внешний или внутренний origin point, откуда пришло значение, запись или утверждение о сущности.

Примеры:
- официальный сайт школы;
- государственный образовательный реестр;
- страница программы на сайте университета;
- PDF-документ о поступлении;
- надёжный образовательный каталог;
- внутренняя ручная нормализация на основе внешнего источника.

Важно:

Источник — это не просто URL.

Источник должен объяснять:
- **кто утверждает данные**;
- **насколько он для этого авторитетен**;
- **насколько источник свежий**;
- **насколько прямо он подтверждает конкретное поле**.

---

## Базовые принципы работы с источниками

### 1. Официальный источник выше вторичного пересказа
Если есть официальный сайт учреждения и есть каталог, приоритет у официального сайта.

### 2. Более прямой источник выше более косвенного
Страница admissions выше обзорной страницы каталога.

### 3. Более свежий источник выше устаревшего
Даже сильный источник теряет ценность, если данные в нём явно устарели.

### 4. Источник должен подтверждать именно то поле, которое мы берём
Нельзя использовать общую страницу школы как безусловное подтверждение для очень конкретных admission details, если их там нет.

### 5. Если источник слабый, это должно быть видно явно
Слабый источник можно временно использовать, но нельзя маскировать его под сильный.

### 6. При конфликте источников нельзя «догадываться в середине»
Если источники конфликтуют, нужна понятная логика приоритета или review, а не неявное смешивание.

# 1. Основные уровни доверия к источникам

## Level 1 — High Trust / Canonical External Sources

Это самый сильный слой источников.

Такие источники могут использоваться как основа для канонической записи без дополнительного понижения trust level, если нет явных конфликтов.

### Сюда обычно относятся:
- официальный сайт учреждения;
- официальный сайт программы;
- государственный образовательный реестр;
- официальный кантональный / федеральный источник;
- официальный документ учреждения;
- официальный PDF / handbook / admissions page;
- официальные API или реестры, если они существуют.

### Почему это high trust
Потому что источник:
- ближе всего к origin owner данных;
- напрямую отвечает за корректность информации;
- чаще всего актуализируется самой организацией или государственным органом.

### Примеры use cases
- название учреждения;
- адрес;
- website;
- contact email;
- admission requirements;
- language of instruction;
- статус программы;
- официальный тип institution.

---

## Level 2 — Medium Trust / Structured Secondary Sources

Это сильные вторичные источники, которые могут быть полезны, но не должны автоматически иметь приоритет над официальными.

### Сюда обычно относятся:
- качественные образовательные каталоги;
- крупные специализированные directory platforms;
- partner pages учреждений;
- reputable informational portals;
- trusted aggregators с понятной методологией.

### Когда они полезны
- когда официальный источник трудно найти;
- когда они помогают быстро собрать первичную структуру данных;
- когда нужно получить дополнительный контекст;
- когда они подтверждаются более сильным источником.

### Ограничение
Такие источники нельзя безоговорочно считать source of truth для критичных полей, если есть расхождение с официальными данными.

---

## Level 3 — Low Trust / Weak Secondary Sources

Это слабые или неполные источники, которые могут помочь найти след, но не должны считаться сильной основой для verified data.

### Сюда обычно относятся:
- малоизвестные каталоги;
- старые directory pages;
- неофициальные списки;
- контент-фермы и перепечатки;
- страницы без понятного origin owner;
- агрегаторы без прозрачной методологии.

### Когда их можно использовать
- для discovery;
- как lead на дальнейшую проверку;
- как временный placeholder с низким trust status.

### Когда их нельзя использовать как основу
- для critical identity fields без верификации;
- для admission requirements;
- для контактов, если они не подтверждены;
- для финального verified status.

---

## Level 4 — Internal Derived / Editorial Layer

Это внутренний слой Inspirella.

Он не является «внешним источником», но может быть важной частью data pipeline.

### Сюда относятся:
- редакторская нормализация описаний;
- объединение нескольких подтверждённых источников;
- вычисленные поля;
- short summaries;
- canonical labels;
- deduplication decisions;
- internal classifications.

### Важный принцип

Internal derived data можно использовать только если:
- понятно, на каких внешних источниках она основана;
- можно проследить цепочку происхождения;
- derived layer не подменяет собой raw source history.

# 2. Типы источников по сущностям

## Для `Institution / School`

Наиболее сильные источники:
- официальный сайт учреждения;
- страница контактов;
- официальная admissions page;
- государственный / кантональный реестр;
- официальные school documents.

Средние источники:
- trusted educational directories;
- institutional partner portals;
- strong overview pages.

Слабые источники:
- непроверенные списки;
- старые зеркала страниц;
- непонятные каталоги без origin clarity.

---

## Для `Program`

Наиболее сильные источники:
- официальный program page;
- admissions page;
- faculty page;
- official curriculum / PDF.

Средние источники:
- trusted program directories;
- comparative educational platforms.

Слабые источники:
- third-party summaries без явной ссылки на official source;
- рекламные списки.

---

## Для `Profession`

Поскольку profession может быть более сложной и менее «единой» сущностью, здесь полезна комбинация источников.

Сильные источники:
- official labor / education / career portals;
- government or institutional profession frameworks;
- official occupational standards.

Средние источники:
- strong career guidance resources;
- trusted educational/career directories.

Слабые источники:
- блоговые статьи без методологии;
- generic SEO pages.

---

## Для `Resource`

Ресурс как сущность сам по себе может быть и источником, и объектом хранения.

Поэтому важно разделять:
- **resource as user-facing object**;
- **source as evidence layer**.

Например:
- официальный educational portal может быть и user-facing resource, и high-trust source;
- случайная справочная статья может быть resource, но слабым source.

# 3. Какие поля особенно зависят от силы источника

Некоторые поля более чувствительны к качеству источника, чем другие.

## Поля с высокой source sensitivity
- `title`
- `institution_type`
- `address`
- `city`
- `country_code`
- `website`
- `admission_url`
- `email`
- `phone`
- `languages_of_instruction`
- `admission_requirements`
- `program_type`
- `status`

Для них особенно важно иметь strong source.

## Поля со средней source sensitivity
- `description`
- `tags`
- `target_audience`
- `short_title`
- secondary metadata

Их можно редакторски нормализовать смелее, но без отрыва от внешней реальности.

## Поля, которые допустимо строить как derived
- `data_confidence_score`
- `source_count`
- completeness score
- internal recommendation support signals
- normalized summaries

# 4. Как фиксировать источник на уровне записи

Для каждой важной записи желательно иметь возможность понять:

- какой у неё primary source;
- какие есть supporting sources;
- когда источник был получен;
- какой у него trust level;
- для каких полей он является основанием.

Минимальный полезный набор для source-tracking:

- `source_type`
- `source_name`
- `source_url`
- `trust_level`
- `retrieved_at`
- `applies_to_entity`
- `applies_to_id`
- `applies_to_fields`
- `notes`

# 5. Что делать при конфликте источников

Конфликт источников — это нормальная часть реальности, а не исключение.

## Общая логика

### Шаг 1. Проверить уровень trust
Источник более высокого trust level обычно выигрывает.

### Шаг 2. Проверить свежесть
Если оба источника сильные, смотреть, какой свежее.

### Шаг 3. Проверить прямоту подтверждения
Если одна страница напрямую описывает admission requirements, а другая только косвенно упоминает их, приоритет у более прямой.

### Шаг 4. Проверить, не относятся ли данные к разным подтипам
Иногда конфликт возникает не потому, что кто-то ошибся, а потому что:
- одна страница относится к institution-wide layer;
- другая — к конкретной program;
- одна — к campus A;
- другая — к campus B.

### Шаг 5. Если конфликт не разрешается автоматически — пометить в review
Нельзя silently принять случайное значение, если конфликт materially important.

---

# 6. Когда источник достаточен для verified status

Источник можно считать достаточным для verified status записи или поля, если:

1. он относится к High Trust или надёжно подтверждён несколькими согласованными Medium Trust источниками;
2. он достаточно свежий;
3. он прямо подтверждает нужное поле;
4. нет сильного конфликта с более приоритетным источником.

Если это не выполнено, запись может быть:
- `provisional`;
- `working`;
- `review_needed`;
- `draft`.

---

# 7. Как будущие ИИ-агенты должны работать с источниками

Это один из самых важных разделов.

Будущие ИИ-агенты должны следовать таким правилам:

## 1. Не придумывать данные
Если источник не найден или слабый, агент не должен уверенно заполнять поле как факт.

## 2. Не повышать trust source без основания
Если источник слабый, агент не должен оформлять его так, будто это official truth.

## 3. Не смешивать raw source и internal summary
Сначала должен быть source trail, потом уже derived summary.

## 4. Явно помечать неуверенность
Если данные provisional, это должно быть отражено в статусе, notes или review queue.

## 5. Не игнорировать конфликты
Если два источника расходятся, агент не должен молча выбрать удобный вариант без логики.

## 6. Предпочитать прозрачность красивой полноте
Лучше неполная, но честная запись, чем «идеально заполненная» запись с выдуманными или слабо подтверждёнными данными.

# 8. Практическая иерархия приоритетов для Inspirella

Ниже — удобная сжатая рабочая версия.

## Source Priority Order

### Priority A — Canonical
- официальный сайт учреждения
- официальный сайт программы
- официальный admissions page
- государственный образовательный реестр
- официальный документ / handbook / PDF

### Priority B — Strong supporting
- trusted educational directories
- strong institutional partner pages
- reputable structured portals

### Priority C — Discovery only
- слабые каталоги
- неофициальные списки
- старые справочные страницы
- сомнительные агрегаторы

### Priority D — Internal derived
- редакторские summary
- canonical naming
- normalized labels
- computed trust / completeness / ranking fields

# 9. Что особенно важно для Inspirella как миссии

Поскольку Inspirella не просто каталог, а система, которая должна помогать человеку находить свой путь через персонализацию, качественные данные и ясность, source layer становится не технической мелочью, а частью сути проекта.

Если источник слабый, то:
- пользователь получает менее надёжную картину;
- рекомендации становятся менее честными;
- ясность превращается в псевдо-ясность;
- персонализация опирается на шаткий фундамент.

Поэтому качественный source hierarchy — это одна из форм реальной заботы о пользователе.
