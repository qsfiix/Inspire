# Testing

## Зачем нужен этот файл

Этот файл нужен для того, чтобы зафиксировать подход Inspirella к проверке качества изменений.

Если:
- `Coding Standards.md` отвечает на вопрос, как писать код;
- `Folder Structure.md` — где этот код должен жить;
- `Dependencies.md` — какие библиотеки допустимы;

то `Testing.md` отвечает на вопрос:

> как понять, что изменение действительно хорошее, ничего важного не ломает и не ухудшает систему.

Этот файл нужен для того, чтобы:
- не полагаться только на ощущение, что «вроде работает»;
- уменьшать риск скрытых поломок;
- поддерживать рост Inspirella как серьёзной системы;
- помочь Sofiia и будущим ИИ-агентам проверять изменения предсказуемо;
- сделать качество изменений частью рабочего процесса, а не случайным бонусом.

# Главная идея тестирования в Inspirella

Inspirella не должна проверяться по логике:

> если экран открылся и ничего сразу не упало, значит всё нормально.

Правильная логика такая:

> каждое значимое изменение должно быть проверено хотя бы на том уровне, который соответствует его риску и влиянию на систему.

Это особенно важно, потому что Inspirella строится как проект, где тесно связаны:
- продуктовая логика;
- data-layer;
- карта и география;
- персонализация;
- интеграции;
- будущие AI workflows.

Поэтому тестирование здесь — это не только про код. Это ещё и про:
- смысловую корректность;
- качество данных;
- устойчивость пользовательских сценариев;
- доверие к системе.

# Базовые принципы тестирования

## 1. Проверка должна соответствовать риску изменения

Не каждое изменение требует одинаковой глубины проверки.

Но чем сильнее изменение влияет на:
- данные;
- recommendation logic;
- карту;
- авторизацию;
- интеграции;
- критические пользовательские сценарии,

тем серьёзнее должна быть проверка.

## 2. Тестирование — это не только automated tests

Для Inspirella важно учитывать несколько уровней проверки:
- ручная быстрая проверка;
- сценарная проверка UX;
- data validation;
- integration checks;
- automated tests, где они действительно оправданы.

## 3. Лучше простая, но регулярная проверка, чем идеальная, но неиспользуемая

На текущем этапе project discipline важнее, чем слишком тяжёлая тестовая система, которой никто не пользуется.

## 4. Проверять нужно не только «работает ли», но и «правильно ли работает»

Особенно для Inspirella это критично, потому что:
- данные могут быть технически загружены, но логически искажены;
- recommendation может что-то показать, но по неправильной причине;
- карта может рендериться, но опираться на плохие координаты;
- UI может выглядеть нормально, но вести пользователя по слабому сценарию.

## 5. Будущие ИИ-агенты должны тестировать изменения консервативно

Если изменение затрагивает важный слой, агент не должен считать задачу завершённой без проверки хотя бы базового сценария последствий.

# Что в Inspirella нужно тестировать в первую очередь

## 1. Критические пользовательские сценарии

Это самые важные пользовательские потоки, где поломка особенно чувствительна.

Примеры:
- открытие главного интерфейса;
- onboarding / profile flow;
- загрузка dashboard;
- отображение карты;
- отображение institutions/programs/resources;
- базовая recommendation/path logic;
- работа ключевых CTA и переходов.

## 2. Data layer

Нужно проверять:
- корректно ли подгружаются данные;
- не сломались ли mappings;
- не теряются ли critical fields;
- не путаются ли сущности вроде `institutions`, `schools`, `programs`, `resources`, `professions`.

## 3. Интеграции

Особенно важно проверять:
- Supabase;
- Mapbox;
- AI-related runtime behavior;
- environment-dependent paths.

## 4. Recommendation / engine logic

Поскольку Inspirella в будущем сильно завязана на персонализацию, engine layer требует особенно аккуратной проверки.

## 5. Public-facing UI consistency

Нужно проверять, что изменения не ухудшают:
- читаемость;
- иерархию;
- понятность интерфейса;
- ощущение качества продукта.

# Основные уровни тестирования Inspirella

## 1. Smoke testing

Это минимальная быстрая проверка после изменений.

### Главная цель
Понять, не сломалась ли система на самом базовом уровне.

### Что обычно проверяется
- приложение запускается;
- ключевые страницы открываются;
- нет очевидных runtime errors;
- не пропали основные данные;
- не сломалась навигация.

### Когда обязательно использовать
Практически после любого заметного изменения.

## 2. Scenario testing

Это проверка реальных пользовательских сценариев.

### Главная цель
Понять, сохраняется ли логика пути пользователя.

### Примеры сценариев
- пользователь впервые открывает продукт;
- пользователь заполняет профиль;
- пользователь смотрит institution/program layer;
- пользователь взаимодействует с картой;
- пользователь получает и интерпретирует рекомендации.

### Почему это важно
Inspirella — это не только код, а продуктовая логика и ощущение маршрута пользователя.

## 3. Data validation testing

Это проверка того, что данные:
- корректно загрузились;
- правильно нормализованы;
- не потеряли критические поля;
- не показывают логических противоречий.

### Особенно важно проверять
- title;
- type fields;
- source-backed fields;
- address and coordinates;
- mapping between raw and normalized shapes.

## 4. Integration testing

Это проверка того, как проект работает с внешними сервисами.

### Примеры
- Supabase connection and reads;
- map rendering through Mapbox;
- AI integration behavior;
- environment-driven runtime logic.

### Почему это важно
Многие проблемы появляются не внутри isolated code blocks, а именно на стыке слоёв.

## 5. Logic testing

Это проверка engine/business logic.

### Что сюда входит
- scoring logic;
- trust logic;
- path logic;
- recommendation helpers;
- normalization behaviors.

### Почему это важно
Эти слои напрямую влияют на качество будущей персонализации.

## 6. Regression testing

Это проверка, что новое изменение не сломало то, что раньше уже работало.

### Главная цель
Не терять устойчивость по мере роста проекта.

### Особенно важно для
- карты;
- onboarding/profile flow;
- data display;
- engine logic;
- integrations.

# Практический минимальный testing workflow

На текущем этапе Inspirella разумно придерживаться такого минимального контура проверки после значимых изменений.

## Шаг 1. Проверить, что проект запускается

Нужно убедиться, что:
- сборка не сломана;
- приложение стартует;
- нет immediate runtime crash.

## Шаг 2. Проверить затронутый сценарий

Если менялась карта — проверить карту.

Если менялся data layer — проверить загрузку и отображение данных.

Если менялась feature logic — пройти соответствующий пользовательский сценарий.

## Шаг 3. Проверить соседние критические зоны

Например:
- если меняли `Repository`, проверить не только один экран, но и другие места, которые зависят от этого слоя;
- если меняли engine logic, проверить не только расчёт, но и то, как он отображается в UI.

## Шаг 4. Проверить, не ухудшилось ли качество данных или UX

Не ограничиваться тем, что «ничего не упало».

## Шаг 5. Зафиксировать, что именно было проверено

Это особенно полезно для future AI-agents и для более зрелой дисциплины проекта.

# Что считать достаточной проверкой на текущем этапе

На текущем этапе проекта разумно считать достаточной проверкой ту, которая:
- покрывает затронутый слой;
- затрагивает хотя бы один реальный пользовательский сценарий;
- проверяет отсутствие явной деградации;
- не игнорирует data/integration side effects.

Это не значит, что нужно сразу строить тяжёлую enterprise-систему тестов.

Это значит, что нельзя завершать работу без осмысленной проверки влияния изменений.

# Что особенно важно тестировать при работе с данными

Поскольку Inspirella глубоко завязана на data-quality, data-related changes требуют более строгой проверки.

## Нужно проверять
- корректность источников данных;
- целостность структуры сущностей;
- совпадение type assumptions;
- отсутствие потери fields;
- отсутствие ложных fallback results;
- географическую правдоподобность location data.

## Особенно опасные зоны
- `institutions` vs `schools`;
- normalized fields vs raw values;
- derived values vs source-of-truth values;
- location and coordinates;
- program and profession links.

# Что особенно важно тестировать при работе с UI

Для UI недостаточно проверить только рендер.

Нужно смотреть:
- читаемость;
- иерархию;
- предсказуемость действий;
- отсутствие визуального хаоса;
- отсутствие сломанных состояний загрузки/ошибки/успеха.

## Базовые UI states, которые желательно помнить
- default state;
- loading state;
- empty state;
- error state;
- success state.

# Что особенно важно тестировать при работе с engine / personalization logic

Это одна из самых чувствительных частей будущего Inspirella.

Нужно проверять:
- не противоречит ли логика данным;
- не даёт ли она случайных рекомендаций;
- объяснима ли выдача;
- не сломан ли баланс между trust, relevance и path logic.

### Важный принцип

Если logic output technically есть, это ещё не значит, что он качественный.

В Inspirella важно проверять и смысловую корректность, а не только технический факт выдачи.

# Когда automated tests особенно полезны

На текущем этапе не обязательно автоматизировать всё подряд.

Но automated tests особенно полезны там, где:
- логика повторяема;
- слой критичен;
- ошибка трудно замечается глазами;
- регрессии будут болезненными.

## Особенно хорошие кандидаты later
- normalization helpers;
- parsing functions;
- engine scoring logic;
- trust logic;
- small reusable data transforms;
- critical utilities.

# Когда ручная проверка обязательна

Ручная проверка особенно важна там, где:
- есть UX-слой;
- есть карта;
- есть product flow;
- есть сложная интеграция;
- есть смысловая оценка результата, которую трудно полностью автоматизировать.

# Что future AI-agents должны делать после изменений

Это один из самых важных разделов.

## 1. Агент не должен считать задачу завершённой без проверки затронутого слоя

Если изменён data layer, нужно проверить data behavior.

Если изменён UI, нужно проверить UI scenario.

Если изменён engine, нужно проверить output logic.

## 2. Агент должен думать о соседних эффектах

Нельзя проверять только самый прямой участок изменения, если известно, что слой используется в нескольких местах.

## 3. Агент должен предпочитать простые, но реальные проверки

Лучше короткая, но осмысленная проверка сценария, чем формальное заявление «должно работать».

## 4. Агент должен явно понимать, что именно он проверил

Это помогает сохранять дисциплину и объяснимость изменений.

## 5. Агент не должен маскировать uncertainty

Если что-то не удалось нормально проверить, это нужно честно обозначить, а не выдавать за завершённую надёжную работу.

# Что считается хорошей testing discipline в Inspirella

Хорошая testing discipline выглядит так:
- важные изменения не остаются без проверки;
- data changes проверяются не только визуально, но и логически;
- critical scenarios периодически прогоняются;
- есть понимание уровней риска;
- ручные и автоматические проверки используются по делу.

# Что считается плохой testing discipline в Inspirella

Плохая testing discipline выглядит так:
- изменения считаются завершёнными без проверки;
- проверяется только тот экран, который меняли напрямую;
- data bugs замечаются слишком поздно;
- карта, источники и recommendation logic не получают отдельного внимания;
- «ничего не упало» считается достаточным критерием качества.

# Testing и миссия Inspirella

Для Inspirella тестирование — это не только техническая безопасность.

Это ещё и защита смысла проекта.

Потому что проект обещает пользователю:
- ясность;
- структуру;
- качественные данные;
- реалистичную поддержку;
- продуманную персонализацию.

Если изменения плохо проверяются, то со временем слабеет всё:
- доверие к данным;
- качество рекомендаций;
- устойчивость UX;
- сила продукта как системы.

Поэтому testing discipline — это одна из форм заботы о будущем качестве Inspirella.
