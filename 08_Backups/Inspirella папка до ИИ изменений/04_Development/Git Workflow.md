# Git Workflow

## Зачем нужен этот файл

Этот файл нужен для того, чтобы зафиксировать рабочий процесс изменений в Inspirella.

Если:
- `Coding Standards.md` отвечает на вопрос, как писать код;
- `Testing.md` отвечает на вопрос, как проверять изменения;
- `Definition of Done.md` отвечает на вопрос, когда работу можно считать реально завершённой;

то `Git Workflow.md` отвечает на вопрос:

> как именно изменения должны двигаться по проекту от идеи и локальной работы до аккуратного, понятного и безопасного сохранения в истории проекта.

Этот файл нужен для того, чтобы:
- не превращать историю проекта в хаотичный набор случайных коммитов;
- сделать изменения понятными для самой Sofiia и будущих ИИ-агентов;
- уменьшить риск потери контекста;
- поддерживать чистую и предсказуемую эволюцию проекта;
- связать код, документацию, data-layer и product-thinking в единый аккуратный workflow.

# Главная идея Git workflow Inspirella

Inspirella не должна развиваться по логике:

> что-то поменяли, как-то сохранили, потом уже постфактум будем разбираться, зачем это было сделано.

Правильная логика такая:

> каждое заметное изменение должно быть достаточно понятным, локализованным и осмысленным, чтобы история проекта сохраняла не только код, но и ход развития системы.

Это особенно важно, потому что Inspirella — это не маленький одноразовый скрипт, а долгосрочный проект, где будут развиваться:
- продуктовая логика;
- данные;
- персонализация;
- интерфейсы;
- документация;
- интеграции;
- работа нескольких ИИ-агентов.

Значит, Git workflow должен поддерживать:
- ясность изменений;
- безопасность правок;
- понятную историю решений;
- возможность спокойно возвращаться к предыдущим шагам.

# Базовые принципы Git workflow

## 1. Один осмысленный блок изменений = один осмысленный шаг в истории

Не стоит смешивать в одном изменении сразу:
- data refactor;
- UI cleanup;
- текстовые правки;
- новую feature logic;
- environment changes,

если они не являются одной логической задачей.

### Почему это важно

Чем чище границы между изменениями, тем легче:
- понимать историю проекта;
- находить источник проблемы;
- откатывать неудачные решения;
- подключать future AI-agents.

## 2. История должна объяснять развитие проекта

Git в Inspirella нужен не просто как техническое хранилище файлов.

Он должен помогать понять:
- что было изменено;
- зачем это было изменено;
- какой блок проекта это затронуло;
- как это связано с общей траекторией развития.

## 3. Лучше меньше, но чище коммитов, чем много шумных и случайных

История не должна превращаться в поток вроде:
- `fix`
- `again`
- `new changes`
- `working version`
- `final final`

Такая история почти не помогает сопровождению проекта.

## 4. Изменения должны быть достаточно безопасными для продолжения работы

После сохранённого состояния должно быть возможно:
- продолжать проект дальше;
- понять, что уже сделано;
- не бояться возвращаться к предыдущим шагам.

## 5. Документация и код должны двигаться достаточно согласованно

Если меняется:
- архитектура;
- data model;
- naming;
- ключевая логика,

то важно не оставлять документацию навсегда в старом состоянии.

# Какой workflow лучше всего подходит Inspirella сейчас

На текущем этапе Inspirella разумно использовать **простой, но дисциплинированный workflow**.

Не тяжёлый enterprise-процесс,
но и не полностью свободный режим без структуры.

Ниже — рекомендуемая логика.

# Этап 1. Сначала понять блок изменения

Перед тем как менять код или файлы, полезно коротко определить:

## Что именно меняется
- data layer;
- UI;
- recommendation logic;
- environment/config;
- documentation;
- project structure.

## Почему это меняется
- новая функция;
- улучшение архитектуры;
- cleanup;
- исправление ошибки;
- усиление данных;
- выравнивание структуры.

## Какой должен быть конечный результат
Это помогает не расползаться в случайные правки по пути.

# Этап 2. Делать изменения блоками, а не хаотично

Хороший рабочий блок изменений — это такой блок, который:
- решает одну понятную задачу;
- не тащит случайно 5 несвязанных вещей;
- может быть понят отдельно от остальных.

## Примеры хороших change blocks
- выровнять `institutions` / `schools` naming;
- добавить `Program` entity documentation;
- вынести repository logic из UI-компонента;
- улучшить карту и location data handling;
- обновить environment variable structure.

## Примеры плохих change blocks
- одновременно менять карту, auth, стили, data model и README без общей логики;
- случайно захватывать unrelated cleanup в ту же пачку;
- смешивать архитектурный рефакторинг и маленький текстовый fix без причины.

# Этап 3. Перед сохранением проверять границы изменения

Перед тем как считать блок готовым к фиксации в истории, полезно проверить:

## 1. Это действительно одна логическая единица работы?

## 2. Тут нет лишнего шума?

## 3. Изменение понятно будущему себе и будущим ИИ-агентам?

## 4. Проверено ли оно хотя бы на разумном уровне?

## 5. Не осталось ли рядом случайных поломанных или полуготовых частей?

# Этап 4. Делать понятные коммиты

Каждый коммит в Inspirella должен быть достаточно понятным по смыслу.

## Хороший коммит должен
- описывать суть изменения;
- быть связан с конкретным логическим блоком;
- не быть слишком общим;
- не быть слишком мутным.

## Плохие коммиты
- `fix`
- `update`
- `stuff`
- `working`
- `final`
- `new version`

## Хорошие коммиты
- `Normalize institutions and schools naming in data layer`
- `Document 03_Data entity rules for programs and sources`
- `Move shared data access into repository layer`
- `Add environment variable rules for runtime integrations`
- `Refine deployment and testing documentation`

# Рекомендуемый стиль commit messages

На текущем этапе Inspirella лучше всего использовать:
- короткое;
- ясное;
- глагольное;
- предметное описание.

## Формула

`Verb + object + scope/result`

## Примеры
- `Add canonical rules for program entities`
- `Refactor map data loading into repository layer`
- `Document Git workflow for Inspirella development`
- `Align environment variable usage across runtime config`
- `Improve testing guidance for data-sensitive changes`

## Важный принцип

Commit message должен объяснять не только «что-то изменилось», а **что именно стало другим**.

# Как работать с документацией в Git workflow

Для Inspirella документация — это не вторичный слой.

Поэтому изменения в документации тоже должны идти осмысленно.

## Когда документацию стоит коммитить отдельно

Отдельный коммит для документации уместен, если:
- меняется только knowledge/documentation layer;
- оформляется новый файл;
- описывается новая часть системы;
- правится структура и смысл без изменений в коде.

## Когда документация может идти вместе с кодом

Если документ прямо сопровождает архитектурное или data-layer изменение, допустимо двигать их рядом, если это один смысловой блок.

### Важный принцип

Документация не должна отставать бесконечно от реальных решений, если решение уже стало каноническим для проекта.

# Как работать с рефакторингом

Рефакторинг — одна из самых опасных зон для хаоса, если у него нет ясных границ.

## Хороший рефакторинг
- имеет понятную цель;
- не смешивается без причины с feature work;
- не маскирует случайные изменения под “cleanup”.

## Плохой рефакторинг
- переписывает слишком много сразу;
- затрагивает unrelated слои;
- ухудшает traceability;
- создаёт риск, который трудно отследить.

## Практическое правило

Если рефакторинг большой, лучше делить его на несколько осмысленных шагов, чем пытаться сделать всё одним коммитом и одной большой путаницей.

# Как работать с экспериментами

Inspirella — проект, где эксперименты неизбежны.

Но эксперименты не должны засорять каноническую историю так, будто это уже зрелое решение.

## Если изменение экспериментальное
Нужно по возможности:
- держать его достаточно изолированным;
- явно понимать, что это тестовая гипотеза;
- не смешивать его с каноническими архитектурными решениями без причины.

## Важный принцип

Эксперимент допустим. Хаос под видом эксперимента — плохой знак.

# Как future AI-agents должны работать с Git workflow

Это один из самых важных разделов.

## 1. ИИ-агент не должен делать слишком широкий change set без необходимости

Если можно решить задачу локально и чисто, лучше не тащить туда половину проекта.

## 2. ИИ-агент должен думать не только о результате, но и об истории проекта

Важно, чтобы после его работы было понятно:
- что он изменил;
- почему;
- как это связано с задачей.

## 3. ИИ-агент не должен смешивать unrelated fixes в одну пачку

Даже если “раз уж заметил, можно и это поправить”.

## 4. ИИ-агент должен уважать границы между кодом, данными, документацией и инфраструктурой

Если изменение пересекает несколько слоёв, это должно быть оправдано и понятно.

## 5. ИИ-агент должен предпочитать изменения, которые легко понять, проверить и при необходимости откатить

Это особенно важно для архитектурных и data-sensitive частей Inspirella.

# Когда изменение не готово к фиксации в истории

Изменение ещё не готово, если:
- логическая задача не доведена;
- результат слишком сырой;
- рядом остались случайные поломки;
- нет базовой проверки;
- слишком много unrelated шума;
- потом будет трудно понять, что именно произошло.

# Практический минимальный checklist перед commit

Перед тем как считать изменение готовым к сохранению в истории, полезно проверить:

## 1. Ясна ли цель этого change block?

## 2. Не смешаны ли тут несвязанные правки?

## 3. Проверено ли изменение хотя бы на базовом уровне?

## 4. Понятно ли по истории, что именно было улучшено?

## 5. Не оставлено ли рядом полуготовое состояние, которое выглядит как done?

Если на эти вопросы ответ неуверенный, скорее всего change block ещё стоит чуть дооформить.

# Рекомендуемый рабочий ритм для Inspirella

На текущем этапе проекта разумен такой rhythm:

## 1. Сначала определить смысловой блок

## 2. Затем внести изменения локально

## 3. Потом пройти базовую проверку

## 4. Потом зафиксировать результат как отдельный чистый шаг в истории

## 5. Потом переходить к следующему смысловому блоку

Это особенно хорошо подходит для Inspirella, потому что проект одновременно растёт:
- как продукт;
- как data system;
- как кодовая база;
- как knowledge structure.

# Git workflow и миссия Inspirella

Для Inspirella Git workflow — это не только инженерная дисциплина.

Это ещё и способ сохранять ясность развития проекта.

Проект, который хочет:
- помогать людям находить свой путь;
- строить высококачественную базу знаний;
- развивать персонализацию мирового уровня;
- становиться сильнее каждый день,

не должен расти как беспорядочная история случайных изменений.

Чистый workflow помогает:
- лучше понимать, как проект развивается;
- не терять сильные решения;
- быстрее замечать слабые места;
- строить Inspirella как зрелую систему, а не как набор временных версий.
