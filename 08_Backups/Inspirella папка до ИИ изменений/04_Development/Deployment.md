# Deployment

## Зачем нужен этот файл

Этот файл нужен для того, чтобы зафиксировать, как Inspirella должна собираться и выкатываться как рабочая система.

Если:
- `Coding Standards.md` отвечает на вопрос, как писать код;
- `Testing.md` отвечает на вопрос, как проверять качество изменений;

то `Deployment.md` отвечает на вопрос:

> как правильно переводить проект из состояния локальной разработки в рабочую среду, не ломая конфигурацию, данные, интеграции и пользовательский опыт.

Этот файл нужен для того, чтобы:
- сделать запуск и выкладку предсказуемыми;
- не путать локальную, тестовую и рабочую среды;
- снизить риск случайных поломок при выкладке;
- помочь Sofiia и будущим ИИ-агентам понимать, что именно должно происходить при деплое;
- поддерживать Inspirella как зрелую систему, а не как набор локально работающих кусков.

# Главная идея деплоя Inspirella

Inspirella не должна жить по логике:

> если локально у меня всё открылось, значит можно просто как-нибудь выкатить это наружу.

Правильная логика такая:

> деплой — это отдельный, осознанный этап жизненного цикла системы, где важно сохранить стабильность, безопасность, корректную конфигурацию и качество пользовательского опыта.

Это особенно важно, потому что Inspirella завязана на:
- environment variables;
- Supabase;
- карту и геослой;
- AI-интеграции;
- data-layer;
- будущую персонализацию.

Ошибки деплоя здесь могут ломать не только внешний вид, но и:
- доступ к данным;
- корректность recommendation logic;
- карту;
- auth/runtime behavior;
- trust пользователя к системе.

# Основные принципы deployment в Inspirella

## 1. Deployment должен быть предсказуемым

Каждый деплой должен идти по понятной логике:
- что именно выкатывается;
- в какую среду;
- с какой конфигурацией;
- после каких проверок.

## 2. Среды должны быть разделены

Нельзя относиться к локальной, тестовой и рабочей среде как к одному и тому же пространству.

Даже если на раннем этапе проект ещё небольшой, логика разделения сред всё равно важна.

## 3. Деплой не должен быть первым моментом, когда система вообще проверяется

До выкладки уже должно быть понятно, что:
- проект собирается;
- ключевые сценарии не сломаны;
- env layer корректен;
- интеграции не очевидно сломаны.

## 4. Секреты и environment variables должны подставляться средой, а не кодом

Деплой не должен требовать ручного хардкода ключей в проект.

## 5. Production stability важнее скорости случайной выкладки

Лучше чуть медленнее, но чище и безопаснее,
чем быстро выкатить сломанное состояние системы.

# Какие среды стоит различать в Inspirella

Даже если сейчас не все из них уже полноценно настроены, архитектурно полезно мыслить их заранее.

## 1. Local development

Это среда локальной разработки на компьютере Sofiia.

### Назначение
- писать код;
- проверять изменения;
- проходить сценарии;
- тестировать новые идеи без риска для рабочей системы.

### Особенности
- использует локальный `.env`;
- может работать с mocks, fallbacks или ограниченными интеграциями;
- допускает более гибкий режим отладки.

## 2. Preview / testing / staging environment

Это промежуточная среда между локальной работой и production.

### Назначение
- проверить, как система ведёт себя в более реальном окружении;
- убедиться, что сборка и env работают как ожидается;
- протестировать интеграции ближе к боевому режиму.

### Почему это полезно
Даже если staging пока ещё не оформлен как отдельная зрелая среда, сама логика staging later будет очень полезна для Inspirella.

## 3. Production environment

Это рабочая пользовательская среда.

### Назначение
- реальный доступ пользователей к продукту;
- рабочий data-layer;
- реальное отображение карты, UI, сценариев и логики.

### Особенности
- самый строгий контроль конфигурации;
- никакого хаотичного debug behavior;
- особенно аккуратная работа с ключами, источниками и качеством данных.

# Что входит в deployment pipeline Inspirella

Ниже — логика того, что вообще должно происходить перед и во время выкладки.

## Stage 1. Подготовка изменений

На этом этапе должно быть понятно:
- какие изменения готовы к деплою;
- какую часть системы они затрагивают;
- есть ли особый риск для данных, карты, AI-слоя или auth.

## Stage 2. Проверка качества перед выкладкой

Перед деплоем нужно убедиться, что:
- проект собирается;
- критические сценарии не сломаны;
- environment variables заданы корректно;
- зависимости не сломали runtime;
- ключевые интеграции хотя бы базово проверены.

## Stage 3. Build

На этом этапе собирается production-ready версия приложения.

### Нужно проверить
- сборка проходит успешно;
- нет критических ошибок;
- не осталось случайных development-only зависимостей или поломанных импортов;
- runtime config не зависит от локальных костылей.

## Stage 4. Runtime configuration injection

На этом этапе среда подставляет нужные значения:
- URL;
- API keys;
- service config;
- server/runtime variables.

### Важный принцип

Конфигурация должна приходить из среды, а не из временно переписанных файлов проекта.

## Stage 5. Deployment execution

Это момент самой выкладки.

На этом этапе важно понимать:
- куда выкатывается система;
- какая версия считается новой;
- какие env values использует среда;
- не затрагивает ли выкладка критические слои данных и интеграций без необходимости.

## Stage 6. Post-deploy verification

После выкладки нужно проверить, что:
- приложение реально открылось;
- не появилось runtime errors;
- главные сценарии живы;
- карта работает;
- данные подгружаются;
- важные интеграции не разрушены.

## Stage 7. Monitoring / rollback awareness

Даже если monitoring later будет ещё усиливаться, уже сейчас важно мыслить, что:
- после выкладки систему стоит наблюдать;
- нужно уметь замечать деградацию;
- при критической проблеме нужен понятный путь отката или исправления.

# Что обязательно нужно проверять перед деплоем

## 1. Сборка проекта

Минимальный уровень:
- приложение реально собирается;
- нет compile-time или obvious bundling issues.

## 2. Environment layer

Нужно проверить:
- все обязательные env values существуют;
- нет случайной подстановки локальных секретов;
- production env не использует local debug assumptions.

## 3. Data-sensitive areas

Если менялся data-layer, нужно проверить:
- не сломались repositories;
- не потерялись critical fields;
- не изменился unexpectedly shape данных;
- не возникла логическая деградация в institution/program layer.

## 4. Map and geospatial behavior

Если затрагивалась карта или location layer, нужно проверить:
- карта рендерится;
- нет сломанных токенов;
- точки и overlays хотя бы базово отображаются корректно.

## 5. AI/runtime integrations

Если затрагивалась AI-интеграция, нужно проверить:
- ключи подставляются корректно;
- приложение не падает при отсутствии ответа;
- runtime path не сломан.

## 6. Core user flows

Нужно пройти хотя бы минимально:
- открытие приложения;
- навигацию;
- загрузку ключевых экранов;
- отображение данных;
- затронутый сценарий после изменений.

# Что особенно опасно при деплое Inspirella

## 1. Смешение сред

Например:
- локальный URL утекает в рабочую конфигурацию;
- production использует неправильный env set;
- тестовые assumptions попадают в live system.

## 2. Тихие проблемы с environment variables

Это один из самых частых классов проблем.

Например:
- переменная существует локально, но отсутствует в рабочей среде;
- ключ подставлен не тот;
- путь к интеграции изменился, а конфигурация осталась старой.

## 3. Data-layer regressions

Если деплой ломает shape данных или доступ к ним, пользователь может увидеть:
- пустые экраны;
- неправильные записи;
- искажённые recommendations;
- слабую карту.

## 4. Map/AI integration failures

Такие вещи могут не всегда ломать всё приложение полностью, но сильно ухудшают продукт.

Поэтому post-deploy verification здесь особенно важен.

## 5. Хаотичный hotfix без понимания слоя проблемы

Если после деплоя что-то ломается, важно не бросаться сразу хаотично патчить всё подряд. Нужно понимать:
- это env issue;
- build issue;
- integration issue;
- data issue;
- UI issue.

# Как future AI-agents должны относиться к deployment

Это один из самых важных разделов.

## 1. ИИ-агент не должен считать деплой нейтральной формальностью

Выкладка — это отдельный рискованный этап, а не просто «последняя кнопка».

## 2. ИИ-агент должен понимать, затрагивает ли изменение production-sensitive слой

Особенно если речь идёт о:
- env variables;
- data access;
- integrations;
- auth;
- map layer;
- engine logic.

## 3. ИИ-агент не должен хардкодить production config ради быстрого успеха

Даже если кажется, что так проще прямо сейчас.

## 4. ИИ-агент должен рекомендовать минимально рискованный путь выкладки

Если change scope большой, лучше:
- сначала локально проверить;
- потом preview/staging logic;
- потом production.

## 5. ИИ-агент должен помнить о post-deploy checks

Даже после успешной выкладки нельзя считать работу завершённой без базовой проверки, что система реально жива.

# Что считается хорошей deployment discipline в Inspirella

Хорошая deployment discipline выглядит так:
- есть понятные среды;
- env layer чистый;
- before deploy есть осмысленная проверка;
- after deploy есть короткая верификация;
- изменения выкатываются предсказуемо;
- production не становится местом случайного эксперимента.

# Что считается плохой deployment discipline в Inspirella

Плохая deployment discipline выглядит так:
- деплой делается без проверки;
- env values путаются между средами;
- проблемы замечаются только после жалоб;
- runtime secrets живут хаотично;
- выкладка зависит от временных ручных костылей.

# Deployment и миссия Inspirella

Для Inspirella deployment — это не просто техническая операция.

Это один из слоёв доверия к системе.

Потому что проект, который хочет:
- помогать людям находить путь;
- давать качественные данные;
- строить сильную персонализацию;
- становиться платформой мирового уровня,

не может опираться на хаотичную и ненадёжную выкладку.

Сильный deployment layer помогает сохранить:
- стабильность;
- доверие;
- предсказуемость;
- качество продукта как системы.
