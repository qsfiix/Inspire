# Definition of Done

## Зачем нужен этот файл

Этот файл нужен для того, чтобы зафиксировать, что именно в Inspirella считается реально завершённой работой.

Если:
- `Coding Standards.md` отвечает на вопрос, как писать код;
- `Testing.md` — как проверять изменения;
- `Deployment.md` — как выкатывать систему;

то `Definition of Done.md` отвечает на вопрос:

> по каким признакам можно честно сказать, что задача или изменение действительно доведены до хорошего состояния.

Этот файл нужен для того, чтобы:
- не закрывать работу слишком рано;
- не путать черновик, промежуточный прогресс и реально готовый результат;
- поддерживать качество проекта по мере роста;
- помочь Sofiia и будущим ИИ-агентам одинаково понимать завершённость;
- удерживать развитие Inspirella в высоком стандарте, а не в режиме случайных полуготовых кусков.

## Главная идея Definition of Done

Inspirella не должна жить по логике:

> если код написан или текст появился, значит работа готова.

Правильная логика такая:

> работа считается завершённой только тогда, когда результат не просто существует, а достаточно ясен, проверен, структурирован и готов к следующему реальному использованию.

Это особенно важно для Inspirella, потому что проект строится как долгосрочная система:
- с качественным data-layer;
- с глубокой персонализацией;
- с большим количеством проектной документации;
- с будущим участием нескольких ИИ-агентов;
- с амбицией расти в платформу мирового уровня.

Значит, «готово» в Inspirella должно означать не формальность, а реальную надёжность результата.

# Что вообще может считаться done в Inspirella

В Inspirella завершённость относится не только к коду.

Работа может быть done на уровне:
- документа;
- задачи;
- фичи;
- data-layer изменения;
- UI-изменения;
- recommendation logic;
- technical cleanup;
- deployment-related change.

Но в любом случае идея одна:

> done = результат можно дальше безопасно использовать как опору, а не как сырой полуфабрикат.

# Базовые принципы завершённости

## 1. Работа должна быть достаточно понятной, а не только выполненной технически

Если результат существует, но:
- неясно, что именно сделано;
- где лежит логика;
- как это использовать дальше;
- зачем принято решение,

то работа завершена не полностью.

## 2. Проверка важна не меньше, чем реализация

Нельзя считать задачу done только потому, что изменение внесено.

Нужно понимать:
- проверялось ли это;
- в каком контексте;
- не сломало ли это соседние части системы.

## 3. Завершённость должна соответствовать риску и масштабу

Чем важнее изменение, тем выше требования к его завершённости.

Например:
- мелкий текстовый fix и изменение data model не должны иметь одинаковую глубину проверки;
- небольшая заметка и канонический документ не должны иметь одинаковый уровень требований.

## 4. «Пока сойдёт» не равно done

Если уже видно, что:
- структура слабая;
- логика хрупкая;
- данные не проверены;
- решение слишком временное,

то это скорее interim state, а не полноценное завершение.

## 5. Временное может быть done только если оно честно помечено как временное

Иногда допустимо закрыть задачу на временном решении, но только если:
- это явно обозначено;
- ограничение понятно;
- не создаётся ложное впечатление, что слой уже зрелый и окончательный.

# Общая Definition of Done для задач Inspirella

Задачу можно считать завершённой, если выполнены все или почти все ключевые условия ниже.

## 1. Цель задачи реально достигнута

Не просто выполнено действие, а достигнут именно тот смысловой результат, ради которого задача создавалась.

## 2. Результат оформлен в понятном месте

Нужно, чтобы результат:
- лежал там, где его логично искать;
- не был потерян в случайных комментариях или разрозненных черновиках;
- вписывался в структуру проекта.

## 3. Нет критичных незакрытых противоречий

Если после выполнения работы остаются ключевые противоречия, которые ломают результат, задачу нельзя считать полностью done.

## 4. Выполнена разумная проверка

Изменение должно быть проверено на уровне, который соответствует его важности.

## 5. Следующий человек или ИИ-агент сможет продолжить без хаотичных догадок

Результат не должен быть «понятен только в моменте автору».

## 6. Если есть ограничения, они явно обозначены

Если работа не идеальна, но готова как текущий этап, это должно быть честно видно.

# Definition of Done для документации

Документ можно считать done, если:

## 1. У документа есть ясная цель

Понятно:
- зачем он существует;
- для кого он написан;
- какую часть системы или проекта описывает.

## 2. У документа есть понятная структура

Документ должен быть:
- логично разбит на главы и подглавы;
- читаемым в VS Code;
- пригодным для быстрого входа в контекст.

## 3. Документ не зависит слишком сильно от устной памяти контекста

Человек или ИИ-агент должен понимать документ даже без полного знания всей переписки.

## 4. Документ достаточно конкретный

Там, где нужна конкретика, не должно быть только красивых общих фраз.

## 5. Документ согласуется с остальной системой файлов

Он не должен противоречить:
- другим каноническим файлам;
- data model;
- structure rules;
- уже зафиксированным решениям.

## 6. Открытые вопросы либо закрыты, либо честно обозначены

Если что-то ещё не решено, это должно быть явно видно, а не скрыто под видом завершённой определённости.

# Definition of Done для кода

Код можно считать done, если:

## 1. Он решает реальную задачу

Код не просто существует, а реально закрывает нужную цель.

## 2. Он достаточно читаемый

Нужно, чтобы:
- названия были понятны;
- структура была разумной;
- ответственность не была хаотично смешана.

## 3. Он не создаёт явный архитектурный долг без пометки

Если решение временное или компромиссное, это должно быть ясно.

## 4. Он согласуется с канонической моделью проекта

Особенно в частях, связанных с:
- data layer;
- institutions / programs / professions / resources;
- source logic;
- engine / recommendation layer.

## 5. Он хотя бы базово проверен

Проверка должна соответствовать изменению:
- smoke check;
- scenario check;
- data check;
- integration check;
- logic check.

## 6. Он не ломает критические соседние зоны

Если изменение затрагивает shared layer, нужно проверить не только локальную часть, но и точки зависимости.

# Definition of Done для data-layer изменений

Data-related задача считается done, если:

## 1. Изменение согласуется с канонической моделью данных

Оно не должно хаотично расходиться с:
- `Data Model.md`;
- `Field Dictionary.md`;
- `Sources.md`;
- `Validation Rules.md`.

## 2. Нет критичной путаницы в сущностях

Например:
- `institutions` и `schools` не смешаны бесконтрольно;
- `program` не спутан с broad category;
- `resource` не спутан с `source`.

## 3. Есть понятный provenance / source logic

Особенно если задача касается новых данных или их переработки.

## 4. Проверена логическая корректность, а не только техническая запись

Нужно понимать, что данные не просто записались, но и сохранили смысл.

## 5. Не усилился хаос в quality/status layer

Изменение не должно silently ухудшать quality discipline системы.

# Definition of Done для UI-изменений

UI-задача считается done, если:

## 1. Экран или компонент работает как задумано

## 2. Не ухудшены читаемость и иерархия

## 3. Проверены основные состояния

Минимально полезно помнить про:
- default;
- loading;
- empty;
- error;
- success.

## 4. Изменение не ломает соседние сценарии

## 5. UI согласуется с логикой продукта

То есть экран не просто красивый, а действительно поддерживает нужный пользовательский путь.

# Definition of Done для engine / recommendation logic

Это один из самых чувствительных слоёв Inspirella.

Задача здесь считается done, если:

## 1. Логика не просто запускается, а имеет смысл

## 2. Она согласуется с данными

## 3. Она не создаёт случайных или труднообъяснимых результатов

## 4. Есть хотя бы базовая проверка смысловой корректности

## 5. Понятно, где проходит граница между current logic и будущим развитием персонализации

# Definition of Done для deployment-related задач

Deployment-related изменение считается done, если:

## 1. Понятно, как оно влияет на среду

## 2. Не сломана конфигурация env

## 3. Изменение прошло разумную pre-deploy проверку

## 4. После выкладки можно выполнить базовую верификацию

## 5. Не создана новая скрытая зависимость от ручного костыля

# Что не считается done

Ниже — важные anti-patterns.

## 1. «Код написан, но не проверялся»

Это не done.

## 2. «Документ есть, но он сырой и нелогично собран»

Это не done.

## 3. «Данные записались, но непонятно, откуда они и можно ли им доверять»

Это не done.

## 4. «UI рендерится, но сценарий пользователя стал хуже»

Это не done.

## 5. «Изменение работает только в голове того, кто его сделал»

Это не done.

## 6. «Есть временное решение, но оно не помечено как временное»

Это не clean done.

# Как future AI-agents должны понимать done

Это один из самых важных разделов.

## 1. ИИ-агент не должен закрывать задачу только потому, что создал артефакт

Написанный текст, изменённый код или созданный файл — это ещё не достаточное условие завершённости.

## 2. ИИ-агент должен думать о пригодности результата для следующего шага

Если другой агент или Sofiia не сможет нормально использовать этот результат дальше, работа ещё не доведена.

## 3. ИИ-агент должен учитывать соседние последствия

Особенно если изменяется:
- shared data layer;
- engine logic;
- UI flows;
- integrations.

## 4. ИИ-агент должен честно обозначать ограничения

Если результат годится только как промежуточный этап, это нужно прямо сказать.

## 5. ИИ-агент должен предпочитать качественное завершение красивой видимости прогресса

Лучше меньше закрытых задач, но более честно и сильно,
чем много формально закрытых, но сырых результатов.

# Практический минимальный чек перед тем, как считать работу done

Перед завершением полезно проверить:

## 1. Цель реально достигнута?

## 2. Результат лежит в правильном месте?

## 3. Нет критичных логических противоречий?

## 4. Изменение проверено на разумном уровне?

## 5. Следующий шаг на базе результата возможен без хаоса?

## 6. Если есть ограничения, они честно обозначены?

Если на несколько этих вопросов ответ отрицательный, скорее всего задача ещё не fully done.

# Definition of Done и миссия Inspirella

Для Inspirella завершённость — это не бюрократический ритуал.

Она нужна потому, что проект строится как система, которая должна:
- нести ясность;
- опираться на качественные данные;
- развивать сильную персонализацию;
- помогать человеку реально двигаться вперёд.

Если в проекте слишком много псевдо-завершённой работы, со временем это разрушает:
- доверие к данным;
- устойчивость кода;
- силу рекомендаций;
- качество UX;
- способность проекта расти без хаоса.

Сильная Definition of Done — это один из способов каждый день делать Inspirella немного более настоящей, надёжной и зрелой системой.
