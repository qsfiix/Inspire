# Checklists

## Зачем нужен этот файл

Этот файл нужен для того, чтобы собрать основные checklists Inspirella для повторяющихся рабочих ситуаций.

Если:
- `Processes.md` отвечает на вопрос, как в целом движется работа;
- `Task Workflow.md` отвечает на вопрос, как живёт задача;
- `Weekly Review.md` отвечает на вопрос, как регулярно смотреть на проект сверху;

то `Checklists.md` отвечает на вопрос:

> какие короткие, практичные списки проверки помогают не забывать важное в типовых ситуациях.

Этот файл нужен для того, чтобы:
- уменьшать количество случайных пропусков;
- не изобретать заново каждый раз один и тот же рабочий алгоритм;
- поддерживать качество без лишней перегрузки;
- помогать Sofiia и будущим ИИ-агентам работать стабильнее;
- усиливать operational discipline проекта без бюрократии.

## Главная идея checklists в Inspirella

Inspirella не должна опираться только на память, настроение и случайную внимательность в моменте.

Правильная логика такая:

> там, где действие повторяется и где легко что-то забыть, полезно иметь короткий checklist, который помогает сохранить качество и ясность.

Checklist нужен не для формальности.

Он нужен для того, чтобы:
- быстро пройти важные точки;
- снизить риск забыть критичный шаг;
- сделать повторяющуюся работу спокойнее и чище;
- не тратить лишнюю энергию на каждый раз заново собираемую последовательность.

## Что в Inspirella считается checklist

Checklist — это короткий прикладной список шагов или проверок для повторяющейся рабочей ситуации.

Хороший checklist:
- короткий;
- конкретный;
- реально используемый;
- не перегруженный лишними пунктами;
- помогает сделать результат сильнее.

Checklist может относиться к:
- началу работы над задачей;
- завершению задачи;
- weekly review;
- документу;
- data-layer изменению;
- UI-проверке;
- деплою;
- проблемной ситуации.

Коротко:

> checklist — это мини-опора для повторяемого качества.

## Когда checklist особенно полезен

Checklist особенно нужен, если:
- действие повторяется;
- у него есть несколько важных шагов;
- легко забыть одну из критичных деталей;
- ошибка потом дорого обходится;
- проверка занимает меньше усилий, чем исправление последствий.

## Когда checklist не нужен

Checklist не нужен, если:
- это единичная нестандартная задача;
- список будет длиннее и тяжелее, чем сама работа;
- он не помогает, а только создаёт рутину без пользы.

## Базовые принципы checklists Inspirella

## 1. Checklist должен быть коротким

Если checklist слишком длинный, его перестают реально использовать.

## 2. Checklist должен проверять важное, а не очевидное ради количества

Нужно включать то, что реально помогает не ошибиться.

## 3. Checklist должен уменьшать хаос, а не создавать новую нагрузку

Он должен быть practical tool, а не мини-бюрократией.

## 4. Checklist должен поддерживать качество, а не заменять мышление

Checklist полезен как опора, но он не заменяет здравую оценку ситуации.

## 5. Future AI-agents должны использовать checklists как дисциплину, а не как формальный ритуал

ИИ должен применять checklist по делу, а не mechanically ради галочек.

# Основные checklists Inspirella

## Checklist 1. Перед началом новой задачи

Использовать, когда появляется новая задача или новый блок работы.

### Вопросы
- Понятно ли, что именно нужно сделать?
- Понятно ли, зачем это нужно проекту?
- Понятно ли, к какому слою это относится: продукт, данные, код, операция, документ?
- Есть ли понятный ожидаемый результат?
- Достаточно ли контекста, чтобы реально начать?
- Нужно ли разбить задачу на подзадачи?
- Нужно ли связать задачу с документом, другой задачей или data-layer блоком?

### Зачем нужен этот checklist

Чтобы не начинать работу на слишком сырой или размытой формулировке.

## Checklist 2. Перед переводом задачи в `In Progress`

Использовать, когда задача кажется готовой к активной работе.

### Вопросы
- Задача действительно приоритетна сейчас?
- Есть ли у неё достаточная ясность для старта?
- Есть ли время и внимание на её реальное движение?
- Нет ли у неё незакрытой зависимости от другой задачи?
- Не будет ли честнее оставить её в `To Do`, если активной работы по ней пока не планируется?

### Зачем нужен этот checklist

Чтобы уменьшать ложные `in progress` задачи.

## Checklist 3. Во время активной работы над задачей

Использовать по ходу выполнения задачи.

### Вопросы
- Я всё ещё двигаю изначальную цель задачи?
- Работа не расползлась в несколько разных направлений?
- Не пора ли разделить задачу, если внутри уже несколько разных блоков?
- Не нужен ли новый документ, подзадача или решение, чтобы удержать ясность?
- Не завис ли блок из-за нехватки данных, решений или структуры?

### Зачем нужен этот checklist

Чтобы активная работа оставалась сфокусированной.

## Checklist 4. Перед закрытием задачи

Один из самых важных checklist-ов.

### Вопросы
- Цель задачи реально достигнута?
- Результат лежит в правильном месте?
- Работа прошла базовую проверку?
- Нет ли критичных незакрытых противоречий?
- Может ли следующий человек или ИИ-агент использовать результат без хаотичных догадок?
- Если есть ограничения, они честно обозначены?
- Задача действительно done, а не просто “почти готово”? 

### Зачем нужен этот checklist

Чтобы статус `done` что-то реально значил.

## Checklist 5. Для нового Markdown-документа

Использовать, когда создаётся новый канонический `.md` файл.

### Вопросы
- Понятна ли цель документа?
- Указан ли `Status`, `Owner`, `Last Updated`, `Purpose`, `Related Files`?
- Есть ли понятная структура с настоящими заголовками `#`, `##`, `###`, `####`?
- Документ читается в VS Code outline нормально?
- Текст достаточно конкретный, а не слишком общий?
- Документ не противоречит уже существующим каноническим файлам?
- Открытые вопросы либо закрыты, либо честно обозначены?

### Зачем нужен этот checklist

Чтобы documentation layer оставался сильным и пригодным для будущих ИИ-агентов.

## Checklist 6. Для data-layer изменения

Использовать, когда меняется data model, сущности, source logic, validation или import behavior.

### Вопросы
- Изменение согласуется с `Data Model.md`?
- Не путаются ли сущности вроде `institutions`, `schools`, `programs`, `resources`, `sources`?
- Не потерялась ли source/provenance логика?
- Нет ли риска data drift или semantic drift?
- Проверено ли влияние на existing data-layer?
- Не ухудшает ли это validation, quality или coverage логику?

### Зачем нужен этот checklist

Чтобы данные не теряли силу под весом быстрых правок.

## Checklist 7. Для UI-изменения

Использовать, когда меняется экран, компонент или визуальный поток.

### Вопросы
- Экран или компонент действительно выполняет нужную задачу?
- Не ухудшилась ли читаемость?
- Понятен ли основной пользовательский путь?
- Проверены ли default / loading / empty / error / success states, если это релевантно?
- Не сломались ли соседние UI-сценарии?
- Не добавилось ли визуального шума без реальной пользы?

### Зачем нужен этот checklist

Чтобы UI оставался не только рабочим, но и понятным и спокойным.

## Checklist 8. Для engine / recommendation logic изменения

Использовать, когда меняется scoring, trust logic, matching или path logic.

### Вопросы
- Логика всё ещё согласуется с данными?
- Не даёт ли она случайных или труднообъяснимых результатов?
- Не маскирует ли она слабые данные красивой выдачей?
- Проверено ли влияние на recommendation behavior хотя бы на базовом уровне?
- Понятно ли, что является current logic, а что later-stage ambition?

### Зачем нужен этот checklist

Чтобы core intelligence layer Inspirella оставался осмысленным, а не случайным.

## Checklist 9. Перед деплоем

Использовать перед выкладкой изменения.

### Вопросы
- Проект собирается?
- Environment variables заданы корректно?
- Ключевые сценарии не сломаны?
- Не затронут ли критично data-layer без проверки?
- Не сломались ли карта, AI integration, auth или runtime-sensitive части?
- Понятно ли, что именно выкатывается?
- Есть ли план хотя бы базовой post-deploy проверки?

### Зачем нужен этот checklist

Чтобы deployment не становился случайным риском.

## Checklist 10. После деплоя

Использовать сразу после выкладки.

### Вопросы
- Приложение открывается?
- Нет ли obvious runtime errors?
- Загружаются ли основные данные?
- Работает ли карта?
- Работают ли ключевые сценарии?
- Не сломана ли конфигурация среды?
- Не появилось ли ощущение скрытой деградации UX или data behavior?

### Зачем нужен этот checklist

Чтобы не считать выкладку успешной только по факту завершившегося deploy step.

## Checklist 11. Для weekly review

Использовать во время еженедельного обзора.

### Вопросы
- Что реально завершено за неделю?
- Что дало ощутимый результат?
- Что сейчас действительно в активной работе?
- Что зависло?
- Какие риски или зоны расползания стали заметнее?
- Что логичнее всего делать дальше?

### Зачем нужен этот checklist

Чтобы weekly review оставался коротким, но сильным.

## Checklist 12. Для stale tasks

Использовать, когда задача долго висит без реального движения.

### Вопросы
- Эта задача всё ещё актуальна?
- Она действительно активна или просто забыта в `in progress`?
- Её стоит вернуть в `To Do`, поставить на паузу или переоформить?
- Её надо разделить на более ясные части?
- Не потеряла ли она связь с текущим фокусом проекта?

### Зачем нужен этот checklist

Чтобы рабочая система не зарастала ложной активностью.

# Как использовать checklists без перегрузки

Checklist-и не должны применяться как тяжёлые обязательные формы для каждой мелочи.

Правильный подход такой:
- использовать нужный checklist там, где он реально помогает;
- не прогонять все checklist-и подряд без смысла;
- держать их как опору, а не как бюрократическую стену.

## Важный принцип

Checklist должен экономить внимание,
а не съедать его.

## 1. Перед началом новой задачи

# Как future AI-agents должны использовать checklists

Будущие ИИ-агенты должны видеть checklists как способ держать качество стабильным.

## Они должны
- выбирать checklist по ситуации;
- использовать его как короткий контроль качества;
- не притворяться, что работа завершена, если checklist явно сигнализирует о слабом месте.

## Они не должны
- механически генерировать галочки без реальной проверки;
- перегружать систему ритуалами;
- превращать checklist в замену мышлению.

### Главный принцип

Checklist должен усиливать здравый operational judgment, а не заменять его.

# Что считается хорошим checklist layer в Inspirella

Хороший checklist layer:
- короткий;
- понятный;
- практичный;
- действительно используется;
- помогает держать стабильное качество.

# Что считается плохим checklist layer

Плохой checklist layer:
- перегружен;
- слишком формален;
- состоит из очевидностей ради объёма;
- не используется в реальности;
- создаёт усталость вместо ясности.

# Checklists и миссия Inspirella

Для Inspirella checklists — это маленький, но очень важный слой operational зрелости.

Проект хочет:
- помогать людям находить путь;
- строить сильную и надёжную базу знаний;
- развивать персонализацию;
- расти как большая, но ясная система.

Такие проекты держатся не только на больших решениях, но и на маленьких повторяемых практиках, которые не дают качеству распадаться.

Хорошие checklists помогают каждый день делать Inspirella чуть более:
- собранной;
- надёжной;
- понятной;
- устойчивой к хаосу.
