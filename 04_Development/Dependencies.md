# Dependencies

## Зачем нужен этот файл

Этот файл нужен для того, чтобы зафиксировать, как Inspirella должна работать с зависимостями.

Если:
- `Coding Standards.md` отвечает на вопрос, как писать код;
- `Folder Structure.md` отвечает на вопрос, где какой код должен жить;
- `Environment Variables.md` отвечает на вопрос, как хранить конфигурацию среды;

то `Dependencies.md` отвечает на вопрос:

> какие библиотеки и пакеты допустимы в Inspirella, по каким принципам они добавляются и как не превратить проект в перегруженную и хрупкую систему.

Этот файл нужен для того, чтобы:
- не раздувать проект случайными пакетами;
- удерживать стек понятным и предсказуемым;
- снижать технический хаос;
- помогать Sofiia и будущим ИИ-агентам принимать более осознанные решения о зависимостях;
- поддерживать архитектуру Inspirella как долгосрочной системы, а не как набора быстрых решений.

# Главная идея работы с зависимостями

Inspirella не должна развиваться по принципу:

> если библиотека может решить локальную задачу, значит её можно сразу добавить.

Правильная логика такая:

> каждая зависимость должна иметь ясную роль, понятную цену и реальную пользу для проекта на более длинном горизонте.

Это особенно важно, потому что Inspirella строится как система с:
- глубоким data-layer;
- растущей персонализацией;
- несколькими интеграциями;
- будущими ИИ-агентами;
- долгим горизонтом развития.

Если зависимости подбираются хаотично, со временем проект получает:
- дублирование ролей библиотек;
- рост сложности сборки;
- больше поверхностей для багов;
- ухудшение читаемости архитектуры;
- большую зависимость от случайных решений раннего этапа.

# Базовые принципы работы с зависимостями

## 1. Каждая зависимость должна иметь явную причину

Нельзя добавлять пакет по логике:
- «вдруг пригодится»;
- «так проще прямо сейчас»;
- «у других тоже стоит».

Для каждой новой зависимости должен быть понятен ответ на вопрос:

> какую конкретную задачу проекта она решает лучше, чем текущие средства.

## 2. Меньше зависимостей — обычно лучше, если это не ломает качество решения

Inspirella не обязана решать всё вручную.

Но если одну и ту же задачу можно решить:
- уже существующим стеком;
- небольшим локальным utility-layer;
- более понятной собственной логикой,

то это часто лучше, чем тянуть новый пакет.

## 3. Зависимости не должны дублировать друг друга по смыслу

Если в проекте уже есть библиотека, которая закрывает определённую роль, нужно быть осторожным с добавлением второй библиотеки для почти той же задачи.

Иначе появляются:
- пересекающиеся abstractions;
- путаница, что где использовать;
- лишний вес в проекте;
- сложность для future AI-agents.

## 4. Архитектура важнее локального удобства

Даже если новая библиотека ускоряет один конкретный кусок работы, её не стоит добавлять, если она:
- конфликтует с текущей архитектурой;
- создаёт лишнюю связность;
- усложняет data-flow;
- делает проект менее понятным.

## 5. Зависимость должна быть понятной не только сейчас, но и позже

Пакет должен быть таким, чтобы через время было всё ещё понятно:
- зачем он нужен;
- где его применять;
- как он вписывается в систему.

# Основные категории зависимостей в Inspirella

## 1. Core framework dependencies

Это зависимости, без которых не существует основной каркас приложения.

Примеры:
- React;
- TypeScript;
- Vite.

### Роль
Они формируют базовую платформу проекта.

### Подход
Такие зависимости меняются редко и требуют осознанного отношения, потому что влияют почти на весь проект.

## 2. Styling and UI dependencies

Это зависимости, которые помогают строить интерфейс и визуальный слой.

Примеры:
- Tailwind CSS;
- motion;
- icon libraries;
- UI helpers.

### Роль
Они отвечают за:
- скорость создания интерфейса;
- консистентность визуального слоя;
- удобство анимаций и UI-поведения.

### Подход
UI-зависимости полезны, но особенно легко разрастаются хаотично, если не контролировать их роль.

## 3. Data and backend integration dependencies

Это зависимости, которые связывают приложение с данными и backend-средой.

Примеры:
- Supabase client;
- PostgreSQL-facing helpers;
- server-side middleware;
- data adapters.

### Роль
Они поддерживают:
- доступ к данным;
- auth;
- sync;
- runtime integration.

### Подход
К таким зависимостям нужно относиться особенно внимательно, потому что они влияют на основу data-layer Inspirella.

## 4. Geospatial and map dependencies

Это зависимости для карт и пространственной логики.

Примеры:
- Mapbox GL JS.

### Роль
Они поддерживают:
- визуализацию географии;
- работу карты;
- later — более сложную location logic.

### Подход
Географические зависимости должны быть хорошо изолированы и не расползаться по проекту без причины.

## 5. AI and intelligence-related dependencies

Это зависимости, связанные с AI-интеграциями.

Примеры:
- Google Gen AI SDK;
- future AI helpers;
- prompt/runtime support libraries.

### Роль
Они нужны для:
- AI-assisted behavior;
- future personalization support;
- intelligent recommendation-related features.

### Подход
Эти зависимости особенно важны для Inspirella, но они не должны превращаться в бесконтрольный слой «магии», который сложно понять и поддерживать.

## 6. Utility dependencies

Это небольшие библиотеки, которые помогают решать общие технические задачи.

Примеры:
- parsers;
- formatting helpers;
- validators;
- small infrastructure utilities.

### Подход
Именно utility-зависимости чаще всего бесконтрольно нарастают. Их стоит подключать только тогда, когда польза реально превосходит архитектурную цену.

# Как решать, стоит ли добавлять новую зависимость

Перед добавлением новой библиотеки полезно пройти короткий фильтр.

## Вопрос 1. Какую конкретную задачу она решает

Нужно уметь сформулировать задачу в одном-двух ясных предложениях.

Если задача неясна, скорее всего и зависимость преждевременна.

## Вопрос 2. Можно ли разумно решить это текущими средствами

Нужно проверить:
- есть ли уже библиотека, которая закрывает этот кейс;
- можно ли решить это существующим стеком;
- можно ли сделать достаточно чистое локальное решение без внешнего пакета.

## Вопрос 3. Не дублирует ли она то, что уже есть

Если пакет дублирует уже существующую роль, его добавление требует особенно сильного обоснования.

## Вопрос 4. Не создаст ли она лишнюю связность

Важно понять:
- придётся ли менять много файлов;
- станет ли новая зависимость центром слишком большого числа решений;
- не усложнит ли она future refactoring.

## Вопрос 5. Насколько она вписывается в долгосрочную архитектуру Inspirella

Нужно смотреть не только на локальную задачу, но и на то, как зависимость:
- сочетается с data-layer;
- сочетается с future personalization;
- влияет на масштабируемость;
- помогает или мешает чистой структуре проекта.

# Когда зависимость почти точно оправдана

Зависимость чаще всего оправдана, если:
- она закрывает существенную системную задачу;
- даёт сильное сокращение сложности;
- хорошо сочетается с текущим стеком;
- не дублирует существующие решения;
- заметно улучшает устойчивость или скорость разработки без архитектурной деградации.

# Когда зависимость скорее не нужна

Зависимость скорее не нужна, если:
- она решает очень маленькую задачу;
- её роль уже дублируется;
- её можно заменить простым локальным кодом;
- она добавляет тяжёлую абстракцию ради слабой выгоды;
- она понятна только в моменте, но плохо вписывается в долгую жизнь проекта.

# Правила для уже существующих зависимостей Inspirella

## React

### Роль
Главный UI framework проекта.

### Подход
Используется как основной каркас интерфейса. Логику не стоит завязывать на неочевидные React-паттерны, если они ухудшают читаемость.

## TypeScript

### Роль
Основа type safety и архитектурной ясности.

### Подход
Типы должны усиливать понятность системы, а не превращаться в шумный уровень сложности.

## Vite

### Роль
Основа dev/build tooling.

### Подход
Считать Vite частью базовой платформы. Не перегружать сборку лишними экспериментальными плагинами без причины.

## Tailwind CSS

### Роль
Главный styling-layer.

### Подход
Использовать последовательно, не смешивая хаотично с несколькими competing styling paradigms без веской причины.

## Express / Node.js server layer

### Роль
Поддержка backend/runtime logic, proxy и server-side control.

### Подход
Серверный слой должен оставаться достаточно понятным и не превращаться в хаотичный промежуточный контейнер всего подряд.

## Supabase

### Роль
Главная backend/data integration база текущего этапа.

### Подход
Очень важная зависимость. Все решения вокруг неё должны быть особенно аккуратны, потому что она затрагивает данные, auth и будущее масштабирование.

## Mapbox

### Роль
Карта и геослой продукта.

### Подход
Нужно держать map-логику достаточно изолированной, чтобы карта не диктовала структуру всему приложению.

## Google Gen AI SDK / Gemini

### Роль
AI-интеграция текущего этапа.

### Подход
Использовать как важный, но не тотально доминирующий слой. Проект не должен архитектурно становиться просто «обёрткой вокруг Gemini».

## Motion

### Роль
Анимации и quality perception интерфейса.

### Подход
Использовать там, где это действительно усиливает UX, а не ради декоративной перегрузки.

# Правила обновления зависимостей

## 1. Не обновлять зависимости хаотично

Обновление пакета — это не нейтральное действие. Оно может влиять на:
- API библиотек;
- сборку;
- runtime behavior;
- интеграции.

## 2. Обновлять осознанно и с пониманием зоны риска

Особенно внимательно нужно относиться к обновлению:
- framework-level пакетов;
- build tooling;
- data/backend integrations;
- AI and map dependencies.

## 3. После значимых обновлений нужно проверять ключевые сценарии

Даже если апдейт выглядит «минорным».

# Правила удаления зависимостей

## 1. Неиспользуемые зависимости не должны оставаться навсегда

Если библиотека больше не нужна, её лучше удалить, чем держать как технический мусор.

## 2. Перед удалением нужно проверить реальные точки использования

Особенно если пакет может использоваться:
- косвенно;
- через shared utilities;
- через старые feature-модули.

## 3. Удаление зависимостей — это часть архитектурной гигиены

Это не второстепенная работа, а один из способов удерживать проект чистым.

# Правила для future AI-agents

## 1. ИИ-агент не должен добавлять библиотеку только ради ускорения локального патча

Если проблема решается небольшим локальным изменением, это часто лучше, чем тянуть новый пакет.

## 2. ИИ-агент должен объяснять причину добавления зависимости

Если предлагается новый пакет, должно быть понятно:
- зачем он нужен;
- что именно он улучшает;
- почему текущий стек недостаточен.

## 3. ИИ-агент не должен дублировать роли библиотек

Если в проекте уже есть рабочий инструмент для похожей задачи, второй пакет нужно предлагать только с очень сильным обоснованием.

## 4. ИИ-агент должен думать о долгом горизонте

Зависимость должна быть оправдана не только «сейчас стало быстрее», но и тем, что она не ухудшит проект через месяцы дальнейшей работы.

## 5. ИИ-агент должен уважать архитектуру Inspirella

Особенно в частях, связанных с:
- data-layer;
- personalization logic;
- integrations;
- product structure.

# Что считается хорошей dependency discipline в Inspirella

Хорошая работа с зависимостями выглядит так:
- стек не раздут;
- у каждой библиотеки есть понятная роль;
- нет лишнего дублирования;
- новые пакеты добавляются осознанно;
- архитектура остаётся понятной человеку и ИИ-агентам.

# Что считается плохой dependency discipline в Inspirella

Плохая работа с зависимостями выглядит так:
- новые пакеты добавляются без системы;
- одна и та же задача решается несколькими competing libraries;
- в проекте много зависимостей, назначение которых уже неясно;
- библиотека становится костылём вместо правильной архитектуры;
- стек начинает жить сам по себе, а не служить проекту.

# Dependencies и миссия Inspirella

Для Inspirella работа с зависимостями — это не просто инженерная аккуратность.

Она напрямую влияет на то, сможет ли проект:
- долго расти без технологического распада;
- поддерживать чистый data-layer;
- безопасно развивать персонализацию;
- интегрировать новых ИИ-агентов без лишнего хаоса;
- становиться всё сильнее, а не всё тяжелее.

Если dependency-layer хаотичен, проект начинает терять ясность ещё на уровне инфраструктуры.

Если dependency-layer дисциплинирован, это поддерживает всю систему и делает дальнейшее развитие спокойнее и устойчивее.
