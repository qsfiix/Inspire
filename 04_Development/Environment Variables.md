# Environment Variables

## Зачем нужен этот файл

Этот файл нужен для того, чтобы зафиксировать правила работы с переменными окружения в Inspirella.

Если:
- `Coding Standards.md` отвечает на вопрос, как писать код;
- `Folder Structure.md` отвечает на вопрос, где какой код должен жить;

то `Environment Variables.md` отвечает на вопрос:

> как проект хранит конфигурацию среды, секреты, ключи и runtime-настройки так, чтобы система оставалась безопасной, понятной и управляемой.

Этот файл нужен для того, чтобы:
- не смешивать секреты с кодом;
- не хранить чувствительные значения в репозитории;
- сделать конфигурацию среды предсказуемой для Sofiia и будущих ИИ-агентов;
- уменьшить риск поломки локальной разработки, деплоя и внешних интеграций;
- отделить то, что является данными проекта, от того, что является настройкой среды.

## Главная идея переменных окружения в Inspirella

Inspirella не должна развиваться по логике:

> если ключ или URL нужен проекту, его можно просто вписать прямо в код.

Правильная логика такая:

> все значения, которые зависят от среды, могут меняться между локальной разработкой и деплоем или содержат секреты, должны жить в переменных окружения, а не в кодовой базе.

Это особенно важно, потому что Inspirella использует и будет использовать:
- Supabase;
- Mapbox;
- AI-интеграции;
- server/runtime layer;
- разные среды запуска.

Если environment layer хаотичен, со временем начинаются проблемы:
- ключи оказываются в коде;
- конфигурация путается между локальной и продакшн-средой;
- ИИ-агенты могут случайно раскрывать чувствительные данные;
- запуск проекта становится непредсказуемым.

## Базовые принципы работы с environment variables

## 1. Секреты не должны храниться в репозитории

Нельзя коммитить в кодовую базу:
- API keys;
- private tokens;
- production secrets;
- реальные credentials;
- чувствительные project IDs, если они должны быть закрыты.

В репозитории может лежать только:
- шаблон;
- пример;
- безопасное описание того, какие переменные нужны.

## 2. Код должен читать секреты только через environment layer

Если приложению нужен ключ, URL или token, код должен получать его из переменных окружения, а не из захардкоженного значения.

## 3. `.env.example` — это описание, а не хранилище секретов

Файл `.env.example` должен:
- показывать, какие переменные нужны;
- объяснять назначение переменных;
- использовать заглушки;
- не содержать реальные секреты.

## 4. Нужно различать чувствительные и нечувствительные переменные

Не все environment values одинаково опасны.

Есть значения:
- чувствительные;
- полу-чувствительные;
- инфраструктурные;
- публичные runtime-настройки.

Это различие важно, чтобы не усложнять всё одинаково, но и не относиться слишком легкомысленно к важным данным.

## 5. Переменные окружения должны иметь понятные имена

Названия должны быть:
- достаточно явными;
- стабильными;
- предсказуемыми;
- понятными человеку и ИИ-агенту.

## 6. Переменные окружения не должны дублировать бизнес-данные

Environment layer нужен для конфигурации среды, а не для хранения содержимого проекта.

Например, в переменные окружения не нужно класть:
- большие контентные блоки;
- продуктовые тексты;
- списки сущностей;
- бизнес-правила, которые должны жить в коде или в data-layer.

## Когда значение должно быть environment variable

Значение стоит выносить в environment variable, если оно:
- зависит от среды запуска;
- может отличаться между локальным запуском и деплоем;
- является секретом или токеном;
- связано с внешней интеграцией;
- является endpoint- или service-specific конфигурацией.

## Когда значение не должно быть environment variable

Значение не стоит выносить в environment variable, если оно:
- является частью канонической бизнес-логики;
- является частью data model;
- является обычной константой приложения, которая не зависит от среды;
- должно контролироваться в коде, а не в окружении.

## Основные категории environment variables в Inspirella

## 1. AI variables

Переменные, связанные с AI-интеграциями.

Примеры:
- `GEMINI_API_KEY`

### Что важно
- такие переменные почти всегда чувствительные;
- они не должны попадать в git;
- они должны использоваться через безопасный runtime path.

## 2. App/runtime variables

Переменные, связанные с runtime-конфигурацией приложения.

Примеры:
- `APP_URL`
- server host/config values
- runtime flags

### Что важно
- часть таких значений может быть не секретной;
- но они всё равно должны быть environment-driven, если зависят от среды запуска.

## 3. Database / backend integration variables

Переменные, связанные с Supabase и другими backend-сервисами.

Примеры:
- `SUPABASE_PROJECT_ID`
- `SUPABASE_URL`
- `SUPABASE_ANON_KEY`

### Что важно
- нужно понимать, какие из них публично допустимы на клиенте, а какие нет;
- даже если ключ технически относится к public/anon-слою, с ним всё равно нужно обращаться аккуратно и не размазывать его хаотично по проекту.

## 4. Map / geospatial variables

Переменные для карты и геослоя.

Примеры:
- `MAPBOX_ACCESS_TOKEN`
- `MAPBOX_STYLE_URL`

### Что важно
- эти значения нужны для работы product experience;
- они должны быть конфигурируемыми;
- они не должны быть жёстко пришиты к коду.

## Текущий минимальный набор переменных среды Inspirella

На текущем этапе разумно считать базовым такой набор:

## AI
- `GEMINI_API_KEY`

## App
- `APP_URL`

## Supabase
- `SUPABASE_PROJECT_ID`
- `SUPABASE_URL`
- `SUPABASE_ANON_KEY`

## Mapbox
- `MAPBOX_ACCESS_TOKEN`
- `MAPBOX_STYLE_URL`

Этот набор уже соответствует текущей логике проекта и может позже расширяться, но именно он сейчас образует ядро environment layer.

## Рекомендуемая структура `.env.example`

Файл `.env.example` должен:
- содержать все обязательные переменные;
- быть безопасным для коммита;
- объяснять, что делает каждая переменная;
- использовать пустые или демонстрационные значения.

Пример логики:

```env
# AI
GEMINI_API_KEY="YOUR_GEMINI_API_KEY"

# App
APP_URL="YOUR_APP_URL"

# Supabase
SUPABASE_PROJECT_ID=""
SUPABASE_URL=""
SUPABASE_ANON_KEY=""

# Mapbox
MAPBOX_ACCESS_TOKEN=""
MAPBOX_STYLE_URL=""
Как работать с .env локально
Локальный .env файл нужен для реального запуска проекта на конкретной машине.

Правила
локальный .env не должен коммититься;
он должен создаваться на основе .env.example;
реальные значения в него вносит владелец проекта или доверенная среда выполнения;
ИИ-агенты не должны переписывать или выдумывать реальные секреты.
Как различать публичные и непубличные значения
Это очень важный слой.

Непубличные значения
Это то, что нельзя раскрывать:

secret API keys;
server-only tokens;
private credentials;
service-level write secrets.
Условно публичные значения
Это то, что может использоваться на клиентской стороне, но всё равно должно храниться аккуратно:

public service URL;
anon/public key, если сервис допускает её использование на клиенте;
map style URL;
некоторые frontend runtime values.
Важное правило
Даже если значение не является сверхсекретным, это не значит, что его нужно хаотично размазывать по коду вместо environment layer.

Как environment variables должны использоваться в коде
1. Через понятный access layer
Код должен по возможности получать environment variables не из случайных прямых вызовов повсюду, а через понятный конфигурационный слой или централизованный доступ.

2. С безопасным поведением при отсутствии значения
Если переменная не задана, код должен:

либо явно сообщить об ошибке;
либо корректно перейти в ограниченный режим;
либо использовать безопасный fallback, если это допустимо.
Но важно
Fallback не должен quietly маскировать критическую проблему конфигурации слишком долго.

3. С разделением client-safe и server-sensitive доступа
Если переменная используется в серверной логике, её не нужно тянуть в клиент без причины.



Если переменная нужна клиенту, нужно понимать, что это действительно допустимо по security-модели.

Чего нельзя делать
1. Нельзя хранить реальные секреты в .md, .ts, .tsx, .json и подобных файлах
Даже если это временно или «просто для удобства».

2. Нельзя коммитить .env с реальными значениями
Это одно из самых важных правил.

3. Нельзя дублировать одно и то же значение в нескольких местах кода
Если URL или token уже идёт через environment layer, он не должен ещё раз захардкоживаться в компоненте, util-файле или engine.

4. Нельзя превращать environment layer в склад случайных флагов
Если появляется новая переменная, у неё должна быть понятная причина.

5. Нельзя смешивать runtime config и product knowledge
Например:

data model не должна жить в .env;
recommendation weights не должны без причины уходить в environment variables;
контент проекта не должен храниться как env-конфиг.
Как future AI-agents должны работать с environment layer
Это один из самых важных разделов.

1. ИИ-агент не должен придумывать реальные значения секретов
Если значение неизвестно, его нельзя выдумывать.

2. ИИ-агент не должен вставлять реальные ключи в код
Даже если это кажется быстрым workaround.

3. ИИ-агент должен различать:
шаблонные значения;
реальные секреты;
публичные runtime values;
server-only sensitive config.
4. ИИ-агент должен сохранять .env.example как документационный слой
То есть:

можно улучшать комментарии;
можно добавлять недостающие переменные;
можно делать структуру понятнее;
нельзя вставлять реальные production/local secrets.
5. ИИ-агент должен уважать границы среды
Если значение относится к:

локальной машине;
деплой-среде;
user secrets в AI Studio;
хостинговой платформе,


то это должно оставаться в своей среде, а не перетекать в код или документацию как будто это часть проекта.

Рекомендуемый подход к naming
Названия переменных лучше делать:

UPPERCASE;
с понятными префиксами;
без двусмысленности;
без случайных коротких названий.
Хорошо
GEMINI_API_KEY
SUPABASE_URL
MAPBOX_ACCESS_TOKEN
Плохо
KEY1
APPSTUFF
TOKEN_FINAL
TEMP_URL
Как environment layer связан с архитектурой Inspirella
Environment layer поддерживает не только безопасность, но и архитектурную ясность.



Он помогает отделить:

код проекта;
данные проекта;
внешние интеграции;
runtime-конфигурацию.


Это особенно важно для Inspirella, потому что проект строится как долгосрочная система, где:

будет расти data-layer;
будет усиливаться персонализация;
будет расширяться число интеграций;
будут подключаться будущие ИИ-агенты.


Если environment layer слабый, проект начинает терять предсказуемость ещё до того, как становится большим.

Environment variables и миссия Inspirella
Для Inspirella правильная работа с environment variables — это не только про безопасность.



Это ещё и про зрелость системы.



Проект, который хочет стать одной из лучших образовательных платформ в мире, не может держаться на хаотичной конфигурации, случайных ключах в коде и неясных runtime-настройках.



Сильный environment layer — это одна из форм инфраструктурной чистоты, которая помогает:

безопаснее развивать продукт;
легче масштабироваться;
меньше ломаться при росте;
удерживать доверие к системе.
Открытые вопросы
когда later выделить отдельный config-layer поверх прямого чтения environment variables;
какие runtime flags позже реально понадобятся, а какие не стоит вводить раньше времени;
как лучше later документировать различие между local, staging и production environment;
какие текущие AI Studio-specific переменные или режимы позже нужно будет отдельно описать как legacy или migration layer.
