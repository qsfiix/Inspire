# Import Rules

## Зачем нужен этот файл

Этот файл фиксирует правила импорта данных в Inspirella.

Если:
- `Data Model.md` объясняет, какие сущности существуют;
- `Field Dictionary.md` описывает поля;
- `Sources.md` определяет иерархию доверия к источникам;
- `Validation Rules.md` объясняет, как проверять записи;

то `Import Rules.md` отвечает на вопрос:

> как именно новые данные должны входить в систему, чтобы база росла структурированно, безопасно и без потери качества.

Этот файл нужен, чтобы:
- не допустить хаотичного добавления записей;
- помочь будущим ИИ-агентам работать по одной логике;
- разделить discovery, normalization, validation и publication;
- уменьшить количество дублей и weak records;
- обеспечить рост базы без разрушения канонической модели.

---

## Главная идея импорта

Inspirella не должна расти по принципу:

> «нашли что-то похожее — сразу записали в базу».

Правильная логика такая:

> **каждая новая запись проходит путь: источник → извлечение → нормализация → проверка → дедупликация → статус → только потом включение в рабочий слой.**

Это особенно важно, потому что Inspirella строится не просто как база, а как система, которая должна давать пользователю:
- ясность;
- качественные данные;
- доверие;
- основу для персонализации.

---

## Общая схема импорта

Любой импорт в Inspirella должен мыслиться как последовательность стадий:

1. **Discovery** — найден потенциальный объект или источник
2. **Extraction** — извлечены сырые данные
3. **Normalization** — данные приведены к канонической форме
4. **Source linking** — привязаны источники и уровень trust
5. **Validation** — проверено качество и логическая целостность
6. **Deduplication** — проверено, не дубль ли это
7. **Status assignment** — назначен статус записи
8. **Persistence** — запись сохранена в appropriate layer
9. **Promotion or review** — запись идёт в usable layer или review queue

# 1. Что вообще можно импортировать

## Основные типы импортируемых сущностей

На текущем этапе Inspirella может импортировать прежде всего:

- `institutions` / school-like entities;
- `programs`;
- `resources`;
- `professions`;
- `sources` как evidence layer;
- позже — more structured user-supporting metadata.

## Что не нужно импортировать как самостоятельную сущность без проверки

Не стоит автоматически импортировать как отдельный объект:

- случайные списки без identity;
- marketing fragments;
- неструктурированные тексты без entity clarity;
- страницы, которые являются только navigation shells;
- вторичные summaries без source clarity.

---

# 2. Базовые принципы импорта

## Принцип 1. Импорт не равен публикации

То, что запись попала в систему, не значит, что она автоматически готова для продукта.

Импортируемая запись может быть:
- raw candidate;
- provisional;
- review-needed;
- usable.

## Принцип 2. Каноническая модель важнее формы исходного источника

Источник может называть сущность как угодно, но в Inspirella данные должны ложиться в каноническую модель.

Например:
- источник пишет `school`, `academy`, `college`, `institution`;
- в системе запись должна быть приведена к канонической сущности и типу.

## Принцип 3. Лучше сохранить источник и uncertainty, чем придумывать missing meaning

Если неясно:
- тип организации;
- полнота адреса;
- точный статус программы;

то это нужно явно отметить, а не заполнять догадками.

## Принцип 4. Импорт должен быть traceable

Для каждой записи должно быть возможно понять:
- откуда она пришла;
- когда;
- кем или чем была импортирована;
- какие поля были извлечены напрямую, а какие нормализованы.

## Принцип 5. Приоритет у качества, а не у скорости наполнения

Лучше медленнее, но чище.

Слишком быстрый импорт без нормализации и проверки создаёт ложный прогресс и потом ломает продукт сильнее, чем недозаполненная база.

---

# 3. Стадия Discovery

## Что происходит на этом этапе

На стадии discovery мы только обнаруживаем, что есть потенциально полезный объект:

- школа;
- программа;
- resource;
- profession-related object;
- источник, который может стать основой для нескольких записей.

## Что важно на этом этапе

Нужно ответить на базовые вопросы:
- это вообще релевантно Inspirella?
- это entity или просто текст/страница?
- это source of truth или просто lead?
- это новая сущность или, возможно, уже известная?

## Результат этапа

После discovery объект должен быть либо:
- допущен к extraction;
- либо отклонён как нерелевантный/слишком слабый.

---

# 4. Стадия Extraction

## Что происходит на этом этапе

Из источника извлекаются сырые данные.

Примеры:
- title;
- address;
- website;
- institution type hints;
- contacts;
- description fragments;
- admission details;
- language info.

## Правила extraction

### 1. Извлекать raw values честно
Не нужно сразу в extraction-stage делать агрессивную интерпретацию.

### 2. Не смешивать raw extraction и canonical meaning
То, что написано в источнике, и то, как это ляжет в Inspirella, — это разные слои.

### 3. Сохранять достаточно raw context
Чтобы later review или agent могли понять, что было в исходнике.

---

# 5. Стадия Normalization

Это один из самых важных этапов.

## Что здесь происходит

Сырые данные приводятся к канонической модели Inspirella.

### Примеры normalization
- `schools` → каноническая institution-логика;
- разные формулировки типа школы → `institution_type` controlled value;
- free-text language names → канонические language codes;
- разные форматы адресов → единый address structure;
- маркетинговое описание → нейтральное, usable summary.

## Важное правило

Normalization должна:
- усиливать ясность;
- уменьшать хаос;
- не искажать смысл исходного источника.

## Нельзя делать в normalization
- придумывать недостающие факты;
- silently заменять uncertainty на уверенность;
- ломать traceability;
- слишком рано выбрасывать важные raw nuances.

---

# 6. Source Linking

После normalization нужно привязать запись к source layer.

## Что должно быть зафиксировано

Минимум:
- `source_type`
- `source_name`
- `source_url`
- `trust_level`
- `retrieved_at`
- какие поля подтверждены этим источником

## Почему это обязательно

Без source linking импортированная запись превращается в «данные без происхождения», а это противоречит самой логике Inspirella.

---

# 7. Validation after import

После импорта запись не должна идти в usable layer автоматически.

Она должна пройти validation по правилам из `Validation Rules.md`.

## Минимум нужно проверить
- identity fields;
- structure;
- source adequacy;
- consistency;
- usability;
- duplicate risk.

## Возможные результаты
- `usable`
- `provisional`
- `review_needed`
- `invalid`

---

# 8. Deduplication before save

Импорт новой записи без проверки на дубль — один из самых опасных путей загрязнения базы.

## Что нужно проверять

### Strong duplicate indicators
- одинаковый официальный сайт;
- одинаковый address + похожий title;
- одинаковые contacts;
- одинаковые coordinates;
- одинаковый source identity.

### Medium duplicate indicators
- очень близкие titles;
- один и тот же institution в нескольких языках;
- несколько записей из разных каталогов с почти одинаковым описанием.

## Что делать при совпадении

### Если это точно дубль
- не создавать новую каноническую запись;
- обновить существующую или привязать новый source.

### Если это вероятный дубль
- отправить в `review_needed`;
- не публиковать как отдельный usable object.

---

# 9. Статусы записи после импорта

После прохождения этапов записи должен назначаться понятный статус.

## `raw_candidate`
Объект найден и частично извлечён, но ещё не прошёл полную обработку.

## `normalized_candidate`
Объект приведён к канонической форме, но ещё не завершил весь review/validation path.

## `provisional`
Запись usable ограниченно, но не fully trusted.

## `usable`
Запись можно безопасно использовать в продукте.

## `review_needed`
Есть конфликт, uncertainty или duplicate risk.

## `invalid`
Запись нельзя использовать как корректную сущность.

## `archived_rejected`
Импортируемый объект признан нерелевантным, ошибочным или дублирующим и убран из активного слоя.

---

# 10. Где должна сохраняться запись

Не все записи должны сразу попадать в один и тот же слой.

## Recommended layer logic

### 1. Staging / import layer
Сырые или частично обработанные кандидаты.

### 2. Canonical entity layer
Записи, которые уже достаточно выровнены по модели.

### 3. Public / product-facing layer
Только те записи, которые готовы для реального пользовательского опыта.

### 4. Review queue
Сюда отправляются записи с конфликтами, weak trust или duplicate risk.

# 11. Import rules for Institution / School

## Когда можно создавать новую institution/school запись

Новая запись может быть создана, если:
- это реально новая educational entity;
- identity достаточна;
- есть source trail;
- нет сильного совпадения с уже существующей записью.

## Когда нельзя автоматически создавать новую запись

- если найден вероятный дубль;
- если непонятно, entity ли это вообще;
- если source слишком слабый;
- если почти все ключевые поля отсутствуют.

## Что особенно важно при school import

- title;
- institution type;
- city/address;
- official website;
- source hierarchy;
- duplicate check against legacy `schools` / canonical `institutions`.

---

# 12. Import rules for Program

Программу нельзя импортировать как самостоятельную сильную сущность, если:
- неясен parent institution;
- title слишком расплывчатый;
- source page не подтверждает existence clearly.

## Good program import
- есть явный institution link;
- есть program page;
- program type понятен;
- admission / duration / language привязаны к source.

---

# 13. Import rules for Resource

Resource можно импортировать быстрее, чем institution, но всё равно аккуратно.

## Нужно проверить
- это реально user-facing resource;
- category понятна;
- URL валиден;
- источник не выглядит мусорным;
- resource не дублирует уже существующий.

## Важно
Resource не должен по ошибке импортироваться как institution только потому, что на странице упоминается школа.

---

# 14. Import rules for Profession

Поскольку professions часто имеют более высокий риск semantic blur, импорт должен быть осторожным.

### Не стоит импортировать profession как полноценную сущность, если:
- это просто keyword;
- это vague job family without clear meaning;
- нет понятного source support.

### Стоит импортировать, если:
- есть ясный occupational identity;
- есть strong enough source;
- profession важна для маршрута персонализации и образовательных связей.

---

# 15. Что будущие ИИ-агенты должны делать при импорте

Это критически важный раздел.

## 1. Не импортировать автоматически всё найденное
Найденное ≠ годное.

## 2. Не пропускать source linking
Каждая meaningful запись должна иметь source trail.

## 3. Не создавать канонические записи до duplicate check
Иначе база быстро расползётся.

## 4. Не заполнять пробелы догадками
Если поля неясны, лучше:
- оставить пустыми;
- пометить provisional;
- отправить в review.

## 5. Не поднимать запись в usable layer без validation
Даже если она выглядит красивой и полной.

## 6. Логировать статус прохождения этапов
Будущий агент должен уметь объяснить:
- что было найдено;
- что было нормализовано;
- что подтверждено;
- что неясно;
- почему запись получила именно такой статус.

---

# 16. Recommended import order for a new record

Практически безопасный порядок такой:

1. Найти объект
2. Проверить релевантность
3. Извлечь raw fields
4. Привязать source
5. Нормализовать поля
6. Проверить duplicate risk
7. Прогнать validation
8. Назначить status
9. Сохранить в правильный layer
10. Только потом продвигать в public/product-facing use

---

# 17. Import and Inspirella mission

Для Inspirella import layer — это не просто технический ingestion.

Это вход в систему доверия.

Если импорт слабый:
- база засоряется;
- структура теряет ясность;
- персонализация строится на шаткой основе;
- пользователь получает менее реалистичную картину мира возможностей.

Если импорт сильный:
- данные становятся надёжнее;
- траектории пользователя становятся реалистичнее;
- будущее масштабирование на страны и сущности становится безопаснее;
- проект остаётся низко-хаотичным даже при росте.
