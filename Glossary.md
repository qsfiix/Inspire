# GLOSSARY

## Зачем нужен этот файл

Этот словарь нужен для того, чтобы фиксировать единые значения терминов внутри проекта.

Он помогает:
- уменьшать неоднозначность;
- не путать похожие понятия;
- быстрее вводить в контекст новые материалы, участников и будущих агентов;
- поддерживать единый язык проекта.

## Правило использования словаря

Если термин часто используется в документации, стратегии, продукте или данных, его лучше зафиксировать здесь.

Если значение термина меняется или уточняется, обновлять нужно сначала этот файл, а затем связанные документы.

---

## Базовые термины

### Inspirella
Рабочее название проекта и всей системы файлов, документов, правил и материалов, связанных с развитием продукта.

### Project structure
Организация папок и файлов проекта, которая нужна для понятного хранения знаний, решений, правил и рабочих материалов.

### Canonical
Статус файла, означающий, что этот файл считается основным источником правды по своей теме.

### Working
Статус файла, означающий, что файл является рабочим черновиком и может меняться.

### Reference
Статус файла, означающий, что файл используется как справочный материал, но не обязательно является основным источником правды.

### Archive
Статус файла, означающий, что файл устарел и не должен использоваться как основа для новых решений.

## Термины смыслового уровня

### Mission
Ответ на вопрос: зачем существует Inspirella.

### Vision
Ответ на вопрос: каким Inspirella должна стать в долгосрочной перспективе.

### Core Principles
Набор принципов, по которым определяется, какие решения для проекта являются правильными, а какие — нет.

### Long-Term Goals
Ключевые долгосрочные цели проекта.

### Positioning
Описание того, для кого существует проект, какое место он занимает и чем отличается.

### Non-Goals
Явно зафиксированный список того, чем проект не занимается и куда не должен расползаться.

---

## Термины стратегического уровня

### Roadmap
Последовательность этапов и направлений развития проекта.

### Feature
Функция, возможность или продуктовый блок, который даёт ценность пользователю или системе.

### Prioritization
Подход к выбору того, что должно делаться раньше, а что позже.

### Risk
Фактор, который может замедлить развитие проекта, ухудшить качество результата или привести к ошибочным решениям.

---

## Термины продуктового уровня

### Architecture
Описание того, как устроен продукт на уровне крупных блоков, связей и логики.

### User Flow
Пошаговый сценарий движения пользователя внутри продукта.

### Screen
Отдельный экран, страница или интерфейсное состояние продукта.

### Requirement
Требование к системе, экрану, процессу, данным или логике.

### Design System
Набор повторно используемых визуальных и интерфейсных правил.

---

## Термины уровня данных

### Data Model
Описание сущностей, их полей, связей и логики структуры данных.

### Entity
Отдельная сущность данных, например школа, программа, локация или источник.

### School
Сущность, обозначающая школу или учебное заведение, которое определяется по правилам проекта. Точное определение фиксируется отдельно в `03_Data/Entities/School.md`.

### Source
Источник данных, из которого берётся информация о сущности.

### Field
Отдельное поле внутри сущности данных.

### Required Field
Поле, без которого запись не может считаться полной или пригодной для использования по правилам проекта.

### Optional Field
Поле, которое желательно иметь, но отсутствие которого не обязательно делает запись непригодной.

### Validation
Проверка данных на соответствие правилам проекта.

### Quality Rule
Правило, по которому оценивается качество данных.

### Coverage
Степень заполненности и полноты данных по сущности, источнику, региону или другому срезу.

### Data Pipeline
Последовательность шагов, по которым данные попадают в систему, проверяются, нормализуются и сохраняются.

### Import Rule
Правило загрузки или переноса данных в систему.

### Field Dictionary
Справочник полей с описанием их смысла, формата и правил использования.

## Термины уровня разработки

### Coding Standards
Правила написания кода, именования, читаемости и структуры.

### Folder Structure
Правила организации папок и модулей внутри технической реализации.

### Git Workflow
Правила работы с ветками, коммитами, изменениями и слияниями.

### Deployment
Процесс выкладки и обновления системы.

### Testing
Подходы к проверке качества реализации.

### Definition of Done
Критерии, по которым задача считается действительно завершённой.

---

## Термины операционного уровня

### Process
Повторяемый способ выполнения определённой части работы.

### Routine
Регулярное действие или цикл работы, который повторяется по расписанию или по необходимости.

### KPI
Показатель, по которому можно отслеживать состояние проекта или прогресс.

### Incident
Ситуация, требующая реакции из-за сбоя, ошибки, потери качества или другого нарушения нормальной работы.
